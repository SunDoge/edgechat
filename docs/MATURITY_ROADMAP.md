# EdgeChat maturity roadmap

The target is a dependable private messenger in the same product class as Delta Chat, not protocol compatibility with Delta Chat and not Matrix compatibility. A green MVP test suite is only the starting point.

## Current baseline

Implemented today: same-server accounts and multi-device identities, OpenMLS text/group messaging, encrypted files, images and voice notes, durable sync plus WebSocket acceleration, Web Push, local PGlite history and full-text search, default-off user-enabled local image semantic search, chunked zstd/R2 archives with authenticated Range reads, room-bound `message:create` notification capabilities with durable ciphertext retry, and resumable MLS device revocation.

Known production caveats remain explicit: no independent cryptographic audit, no server-assisted account recovery, no completed accessibility/browser matrix, and no federation. Default onboarding now asks only for a nickname and generates an opaque namespaced ID plus high-entropy account credential; D1 retains only its verifier. The credential is carried inside encrypted portable backups and target-device-bound linking envelopes, while every endpoint still has an independent MLS identity. A legacy password-verified, metadata-only user appeal and operator resolution workflow remains available, but it intentionally cannot replace lost MLS keys. Authenticated password-encrypted local device backup/restore is implemented, including MLS state and local plaintext history. QR/camera device linking, public-key fingerprints, explicit approval, per-room MLS Add tasks, proof-of-key session claim, reload-safe client state, and progressive device-to-device history handoff are implemented. The account-credential envelope remains in D1; history handoff alone uses independently authenticated, resumable 16 MiB R2 bundle shards and deletes each temporary shard after durable local staging.

## Release gates

### Gate 1 — data safety and predictable cost

- [x] D1-backed per-user R2 byte and object accounting.
- [x] Atomic quota reservations before R2 writes and rollback after failed writes.
- [x] Client-hash and stream normal encrypted attachment and archive-segment uploads through a Worker `FixedLengthStream`; archive validation buffers only the bounded framing/key-envelope prefix, while attachment and archive repair uploads stream against their D1-pinned digest. R2 verifies SHA-256 during the single normal PUT, so neither `Content-Length` nor a whole-ciphertext Worker buffer is trusted.
- [x] Client-ID idempotent, cancellable, and crash-cleaned attachment upload: every 192-bit opaque ID for a bounded multi-part send is journaled in PGlite before its first PUT and bound in D1 to uploader, room, length and ciphertext digest. One automatic retry after an ambiguous response reuses it, costs zero object calls after D1 commit, and uses only a conditional PUT plus at most one exact HEAD in the post-PUT/pre-D1 crash window. A caught failure or restarted PWA checks outgoing MLS staging/outbox/message evidence before one batch abandonment; durable sends are never deleted, while unqueued exact claims/objects and caches are reclaimed without LIST, discovery HEAD, or a seven-day wait. Offline cleanup remains durable for reconnect retry.
- [x] Crash/lost-response archive upload recovery: compaction retries once with the preallocated segment ID and byte-identical ciphertext; a committed D1 row answers before object-store access, exact range/size/digest conflicts are rejected, and a terminal ambiguity is resolved without LIST. Crash-left `uploading`, unknowable `upload_unknown`, and interrupted post-commit `uploaded` jobs remain durable and block replacement compaction for that room until startup/reconnect recovery finishes. A committed segment proceeds to OPFS retention acknowledgement; otherwise a D1 cancellation marker plus exact DELETE closes the late-PUT race and returns quota once. The uploader revalidates its lease before D1 commit, local repair ciphertext survives unknown state, and cancellation never removes a committed segment.
- [x] Avoid tiny archive objects: compact at 1 MiB input or 500 events.
- [x] User quota UI with attachment/archive split and warning thresholds.
- [x] D1-only Operator totals and configurable per-user byte/object overrides, without bucket listing.
- [x] Crash-safe D1 write intents, bounded orphan cleanup, and on-read missing-object quota repair without routine bucket listing.
- [x] Read-only, bounded-memory offline operator audit for legacy/manual R2 or S3 objects that predate or bypass the write-intent ledger. Both providers page at most 1,000 current names per request, enforce an explicit LIST-request budget, report the exact request count, and never fetch object bodies; B2 hidden-version lifecycle verification remains a separate release gate.
- [x] Seven-day cleanup for uploaded attachments that never become referenced by a durable event.
- [x] Sender-only deletion/tombstone flow that removes local search content and decrements usage only after attachment object deletion succeeds.
- [x] Paginated account export plus resumable account deletion covering local plaintext, exact-key R2 cleanup, private-room Durable Objects, shared-room ownership transfer, and client-produced MLS Remove Commits. Export pages stream to a native file or profile-scoped OPFS with exact crash/failure cleanup; the 64 MiB whole-Blob fallback is bounded, and D1 object manifests never read/copy R2 bodies.
- [x] Durable message outbox with unchanged-ciphertext retry, event-ID idempotency, reload recovery, exponential backoff and visible send states. Real Chromium now verifies an OPFS-backed offline enqueue across database-Worker restart, browser online-event drain, accepted-event projection and local FTS without any object-storage request.
- [x] Client-only backup/restore with versioned, chunk-authenticated encrypted PGlite, device-key, and OpenMLS snapshots; checkpoint creation, vault persistence, portable identity export and the physical PGlite snapshot share the global MLS mutation critical section, so incoming/outgoing ratchets cannot split the two halves of a backup. Repeated restores therefore do not accumulate old databases. Whole-Blob fallback is capped at 128 MiB, interrupted/crash-left staging is cleaned, and no R2/S3 copy is created.

- [x] Typed Dexie wrappers for device keys and temporary browser staging, preserving existing IndexedDB schemas while leaving PGlite storage exclusively under PGlite control.
- [x] User-initiated browser persistent-storage protection with approximate origin quota pressure, explicit best-effort/unsupported states, and clear separation from cloud R2 quota and encrypted backup; zero network or object-storage traffic.

Durable multi-device event, attachment, and archive coverage acknowledgements are implemented. Acceptance receipts use a bounded active-plus-historical secret keyring, fail-closed validation, and an operator-only key-ID health endpoint, so rotation preserves old repair receipts. Never resurrect intentionally collected data below the server floor.

- [x] D1-only, paginated room-retention inventory and HTTPS-only operator CLI for policy inspection and updates without R2 listing.

## R2/S3 budget policy

R2 is the encrypted blob/archive plane, never the live event database or search index.

- [x] All production object-plane access is behind an exact-key provider-neutral `ObjectStore` contract with no list operation. Native R2 and path-style SigV4 S3/B2 adapters cover metadata, signed SHA-256 rejection, create-if-absent writes, normalized strict Range reads and batch exact-key deletion; D1 remains authoritative and one provider is selected per deployment.
- [ ] Run and record the checked-in, explicit-confirmation live object-store contract against a real B2 staging bucket, including conditional streaming PUT, payload-hash rejection, metadata, strict Range and exact batch cleanup, and verify a hidden-version lifecycle policy before advertising B2 as production-ready or physical quota reclamation as immediate. The runner reuses the production adapter, makes seven requests on success with no LIST/full GET, and is excluded from normal test/release commands.

- Attachments use one opaque object because they have independent authorization and deletion lifecycles. Do not create thumbnail objects by default. A sending device may place an at-most 8 KiB image thumbnail inside the MLS-encrypted message, under a 40 KiB aggregate message budget; this creates no additional object operation and only increases bounded event/archive bytes.
- Attachment reads are OPFS-first and single-flight per opaque ID. Timeline and media-library images may render the bounded E2EE thumbnail and silently upgrade only when original ciphertext is already in the profile's OPFS cache; a cache miss requires an explicit original-load action, just like voice playback and file saving, so scrolling cannot create speculative R2/S3 GETs. Concurrent explicit render/save consumers share one cold object read, successful retention acknowledgements are coalesced for the app session, and zero-copy forwarding aliases any available local ciphertext without an object read or write.
- Profile avatars use one current client-resized WebP object per account, capped at 128 KiB. They are quota-accounted, content-addressed for idempotent retry, addressed publicly only through an opaque active ID, and replaced through an exact-key deletion ledger; no old versions or server thumbnails are retained. The normal healthy path remains one PUT plus one exact old-key DELETE. Routine GC waits out the write-intent window and a second different avatar is rejected while prior exact cleanup is unresolved, adding no LIST/HEAD/GET request. A missing/corrupt read creates one D1 repair job, suppressing subsequent GETs until the owner supplies the exact original bytes; repair performs one checksum-verified PUT to the same key and no LIST/HEAD or quota mutation.
- Group avatars use the ordinary encrypted attachment plane but are restricted to one current client-resized WebP object per group, capped at 128 KiB plaintext. MLS carries the decryption metadata; D1 tracks only the opaque current object. Name-only changes reuse it, replacement/removal uses exact-key deletion, active avatars are excluded from retention GC, and the UI reads OPFS-first and lazily. No thumbnail or version objects are created.
- Membership and leave workflows use D1, Durable Objects, content-free sync/Push hints and device-local MLS state only; their R2/S3 object/read/write/list budget is exactly zero.
- A voice note is one ordinary encrypted attachment object. Timeline rendering must not auto-fetch it; the first explicit play/save action performs the authorized object read. Do not create server-side waveform, transcoding, or alternate-codec objects.
- Device-local retention deletes local decrypted projections, indexes, and matching signed repair envelopes. It performs no R2 request and must not be presented as cloud quota reclamation; sender retraction/account deletion remain the flows that can schedule exact-key attachment deletion.
- Historical messages are packed into 1–10 MiB range-decodable segments. A low-volume room waits until at least 1 MiB of encoded input or 500 events, whichever comes first.
- D1 metadata is authoritative for object location and accounting. Normal request paths must not call bucket `list()` or `head()` merely to discover objects.
- Once a missing attachment or archive segment has a D1 repair job, subsequent downloads must fail from D1 without another R2 GET until a verified conditional repair clears the job.
- Each historical lookup first uses an exact complete OPFS segment if present, then a profile-scoped authenticated header/envelope/index cache, and only then R2 Range reads. A cold remote lookup fetches one framing header, one coalesced device-key-envelope/encrypted-index range, then encrypted chunk ranges. Require exact partial-content responses and reject whole-object fallback.
- The history manifest returns at most four segments immediately before the requested room sequence. Continue with the earliest returned `start_seq`; never return the room's complete segment catalog on every page.
- Standard storage is the default. Infrequent Access is opt-in only after measured access patterns justify its higher operations/retrieval cost and minimum storage duration.
- Bucket lifecycle deletion must not be enabled for committed `attachments/` or `rooms/` prefixes until the administrator retention floor/generation and deletion-event reconciliation keep D1 and clients consistent.
- Cloudflare is the reliable new-device bootstrap and temporary encrypted snapshot relay. Future native iroh and browser WebRTC paths are optional bulk-transfer optimizations behind one peer-transport boundary; browser iroh is relay-only and must not be advertised as LAN-direct.
- Temporary/multipart prefixes may use short lifecycle cleanup. Failed single-part uploads are deleted immediately and quota reservations are rolled back.
- Device linking uses temporary, quota-accounted `device-links/<link>/<transfer>/<index>.bin` objects over one versioned bundle containing the gzip PGlite snapshot and cached attachment ciphertext. Plaintext shards are 16 MiB, encrypted directly from the approving device's ECDH key to the new device, deleted individually after authenticated durable local staging, and exact-key reclaimed immediately on explicit cancellation or when an unclaimed 24-hour link expires (with cron as the offline backstop). Cleanup follows D1's manifest and performs no list/head request; pending links and cancellation before history upload use zero object operations. Bundles are never split per room, message, or attachment; a 1 GiB bundle produces about 64 objects.
- Default deployment budget is 2 GiB and 100,000 objects per user, configurable through `USER_OBJECT_QUOTA_BYTES` and `USER_OBJECT_LIMIT`.

## Evidence required before calling this a Delta Chat alternative

Completion requires more than matching a feature checklist: multi-month dogfooding, upgrade and recovery drills, independent cryptographic review, load/cost measurements, cross-browser/mobile testing, accessibility review, and published operational/security documentation. Until those gates pass, project documentation and UI should describe EdgeChat as an MVP or preview.
