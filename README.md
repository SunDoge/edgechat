# EdgeChat

For browser-free Worker/RoomDO/MLS testing and the trusted CrossGram gateway
boundary, see [docs/CROSSGRAM_GATEWAY.md](docs/CROSSGRAM_GATEWAY.md).

EdgeChat is a web-first, self-hostable encrypted messenger for Cloudflare Workers. Phase 1 is deliberately single-server: IDs are globally namespaceable, but every remote-domain operation is rejected. The room home server assigns one monotonically increasing sequence number, so the core never inherits Matrix DAGs, multi-writer state resolution, or federation complexity.

The PWA is the install-free baseline client and commits to text, image, recorded-voice, and file messaging plus the E2EE, local history, offline outbox, and durable foreground sync they require. Browser-controlled background delivery and OS integration are best effort and are labelled in the account UI with a recovery path; a later native app will own the complete platform experience without forking the protocol. See [`docs/CLIENT_STRATEGY.md`](docs/CLIENT_STRATEGY.md).

> **Security status:** this is an MVP, not an audited secure messenger. Chat messages and membership changes use OpenMLS 0.9 implementing RFC 9420, compiled to browser Wasm. The selected suite is `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. WebCrypto remains responsible for the outer device/request signature and independently encrypted attachments. CSP and baseline browser/API hardening are enabled, and the local-data/coordination browser gate runs in Chromium, Firefox and WebKit, but production still requires protocol review, recovery design, real-device iOS/mobile validation, and an independent cryptographic audit. See [SECURITY.md](SECURITY.md).

## Architecture

```text
SolidJS PWA
├── UI / VisualViewport / IME-safe composer
├── PGlite worker ── OPFS AHP (IndexedDB fallback)
├── local plaintext FTS
├── local CLIP image embeddings (dedicated Worker)
├── device keys + E2EE provider
└── durable /sync + WSS with shared HTTPS fallback + Web Push
                 │ HTTPS / WSS
                 ▼
Cloudflare Worker
├── auth + HTTP API
├── SunDoge/kysely-d1 ─────────────── D1
├── one-time WebSocket tickets         users, devices, rooms,
├── exact-key ObjectStore boundary     membership, sync log,
└── room-name routing                  archive metadata
                 │
                 ▼
Room Durable Object (one per room)
├── authoritative room-local sequence
├── membership validation
├── idempotent event acceptance
├── SQLite recent history
└── hibernatable WebSocket fanout
                 │
                 ▼
R2ObjectStore (default)
├── opaque encrypted attachments
└── chunked encrypted archive segments
```

The Durable Object is the serialization authority. It persists an accepted event, mirrors ciphertext into D1's durable per-user sync log, then broadcasts it. WebSocket loss therefore affects latency, not delivery: reconnect always repairs gaps using `/api/v1/sync?cursor=...`. After three consecutive room-socket failures, the PWA coalesces all affected rooms into one randomized 4–7 second HTTPS cursor poller and probes WSS recovery at low frequency. A profile-scoped device setting may force that HTTPS-only path before any WebSocket ticket or socket is created; switching either direction performs durable catch-up and survives reload without becoming server account state. The compatibility status is visible because typing/presence can lag, while messages remain fully usable; the device/account panel exposes the switch, one bounded manual realtime retry for automatic fallback, and the browser's proxy limitations. Realtime sockets negotiate an optional mixed-version-safe wrapper that pads small frames into fixed 256–4096-byte buckets; it changes network byte counts only and never enters D1 or R2/S3. Either HTTPS fallback mode adds coalesced D1 reads but performs no R2/S3 operation. `@edgechat/sync` also exposes one injectable outer `NetworkRoute` for both Fetch and realtime creation, allowing a future native shell to use a system proxy or VLESS adapter without forking MLS, sync, room ordering, or storage semantics; the PWA retains the browser route. ECH, padding limits, HTTP/3 caveats and native system-proxy/VLESS/MASQUE boundaries are documented in [`docs/TRANSPORT_RESILIENCE.md`](docs/TRANSPORT_RESILIENCE.md).

Worker object-plane code depends on a narrow provider-neutral `ObjectStore` contract: exact-key put/get/head/delete, normalized byte ranges, metadata, SHA-256 verification, and create-if-absent writes. The default adapter uses the native R2 binding; a path-style SigV4 adapter supports deployment against Backblaze B2, AWS S3, or MinIO-compatible endpoints. The contract deliberately exposes no bucket listing, so normal request paths cannot become catalog scans. D1 remains authoritative for object keys, byte/object accounting, digests, retention, and repair jobs. One deployment selects one object provider; mirroring or dual writes are not the default. Live B2 staging validation and hidden-version lifecycle verification remain release gates; see [`docs/OPERATIONS.md`](docs/OPERATIONS.md#selecting-an-s3-compatible-provider).

`pnpm test:object-store:live` is the explicit staging-provider gate. It reuses
the production S3 adapter, requires a bucket-bound write/delete confirmation,
uses seven requests on success, performs no LIST or full-object GET, and is never
included in ordinary test or release commands.

## Frontend boundary

The visual layer uses SolidJS and Tailwind CSS v4. Theme tokens live in `apps/web/src/styles.css`; reusable, framework-neutral class contracts are exported from `@edgechat/ui/styles`. Components in `@edgechat/ui` are thin Solid browser-behavior adapters for VisualViewport, scroll anchoring, textarea sizing, and IME-safe submission.

Keyboard and assistive-technology behavior is part of the client contract: dialogs isolate background content and trap focus, action menus implement labelled Arrow/Home/End/Escape navigation, selected conversations retain native button semantics, and disabled composers expose their reason. The current interface is `zh-Hans`; the remaining deployed screen-reader/browser/zoom matrix and future string-catalog boundary are documented in [`docs/ACCESSIBILITY.md`](docs/ACCESSIBILITY.md). These behaviors are entirely local and create no D1, R2, or S3 traffic.

SolidJS is confined to `apps/web` and `packages/ui`; the protocol, crypto, database, sync, and Worker packages remain framework-independent. Complete static class strings are preferred over dynamically constructed Tailwind class names so monorepo source detection remains deterministic.

Image semantic search is default-off and lazy-loaded. Only the explicit **允许下载并开启** action allows its exact model/runtime bundle to be fetched on first use; ordinary image viewing, indexing, text search, application startup and PWA installation make no model request. The consent record is profile-scoped and bound to the CLIP repository commit, quantization, Transformers.js version and ONNX Runtime build. Changing any downloadable artifact therefore returns the feature to off instead of silently fetching an upgrade. The CLIP request uses a full immutable Hugging Face commit revision, and the browser dependency/runtime URLs use exact versions. They are not stored in R2. Turning the feature off terminates its Worker and removes image vectors from the current profile's PGlite database. The shared model download remains under browser-managed site/cache storage and must be removed through browser site-data controls when the user wants those bytes reclaimed. The runtime is served from jsDelivr because the upstream 4.3.0 asyncify Wasm exceeds Cloudflare Workers' per-static-asset limit, while Transformers.js maintains its own browser cache for subsequent/offline use. Operators that require a fully self-hosted first run should mirror these immutable public artifacts on a dedicated static origin and update the CSP; do not put them into each user's R2 quota.

Small native CSS rules remain appropriate for browser behavior and pseudo-elements. Product layout and component styling should otherwise prefer Tailwind utilities and shared theme tokens rather than adding new page-specific selectors.

## Threat model and E2EE boundary

The intended protection is against an honest-but-curious or compromised storage/transport server reading message bodies and attachment contents. Message encryption, attachment encryption, group-state wrapping, decryption, and indexing occur on clients. The server never receives a room plaintext key, plaintext attachment filename, plaintext message, or plaintext search index.

The server can still see metadata required to operate the service:

- account IDs, display names, profile bios, opaque active-avatar IDs, avatar image digests/sizes, account-credential verifier material, device IDs, public device keys, and opaque device-backup checkpoint hashes/counts/timestamps;
- room IDs, home domain, personal-bot room labels, membership, roles, room type, sequence numbers, timestamps, event types, and ciphertext sizes;
- IP/network metadata available to Cloudflare, active WebSocket connections, opt-in room presence, device-enabled read-receipt event timing and ephemeral typing sender/timing, push endpoints and hashed renewal capabilities, per-device room mute expiry, direct-user block relationships, per-account group-hidden member IDs, message-request participants/status/report category and optional event ID, account-appeal category/status/timestamps and internal operator note, encrypted-draft room/source/target device IDs, update timing and ciphertext size, per-device acknowledged local sequence coverage and attachment-cache possession, R2 object sizes, ciphertext SHA-256 digests, and access timing;
- TLS-serialized MLS KeyPackages, Welcome messages, ratchet trees, MLS epochs and ciphertext sizes; encrypted attachment/segment object IDs, opaque current/previous group-avatar attachment IDs, cross-room attachment-forward grants, delivery cursors, capability-bound Bot ID/provenance markers, and the opaque target event ID used to authorize deletion, edits, and reactions. Group-avatar keys, nonces and media metadata, reply/quote targets, quote snapshots, Bot display labels, and forwarded message contents remain inside MLS ciphertext.

E2EE does **not** protect a compromised endpoint. PGlite intentionally contains decrypted messages, unsent text drafts, local full-text indexes, and image embeddings that can reveal image semantics. Device private `CryptoKey` objects are stored in browser IndexedDB. Keys created after portable-backup support are extractable so they can be wrapped into an explicitly requested password-encrypted backup; ordinary application storage still never serializes them as plaintext JWK. Browser profiles, OS backups, extensions, malware, notification surfaces, screenshots, and a stolen backup plus its password remain in scope for endpoint security. Local encrypted-at-rest storage is an interface boundary, not implemented in Phase 1. Removing a local profile closes and terminates its PGlite Worker, durably records an exact physical-deletion intent before removing profile metadata, and reloads. The new document deletes every recorded profile-owned OPFS/IndexedDB database slot before it can create another PGlite Worker; failure retains the intent and stops startup. SQL row deletion alone is not treated as plaintext erasure. This cannot erase copies retained by browser/OS backups or a compromised endpoint. Portable backup encryption is chunked and streamed directly to a native file when available, otherwise into a profile-scoped encrypted OPFS staging file before download; only bundles up to 128 MiB may use the whole-Blob memory fallback when neither capability exists. Export staging never contains plaintext. Restore authenticates each encrypted chunk and streams the decrypted local-history bundle into a separate profile-scoped OPFS file instead of retaining it in memory; its PGlite member is endpoint plaintext, while included attachment/archive members remain inner E2EE ciphertext. Failure removes its exact partial file, success removes it after database staging, startup removes crash leftovers before normal use, and profile removal clears both staging areas. The device panel reports the browser's approximate origin-wide local usage/quota separately from R2 quota and exposes `navigator.storage.persist()` only behind an explicit user action. A granted persistent bucket protects against automatic user-agent eviction, not explicit site-data deletion, device loss, corruption or compromise; portable encrypted backup remains necessary. The local profile registry records only when a backup was created and whether the browser confirmed a native-file write or merely started a download; the settings surface recommends a first or refreshed backup after 30 days and never claims an unverified download was saved. This health record and the backup remain device-local. Inspecting local storage, portable-backup export, and local staging create no Worker, D1, R2 or S3 request; restore retains its existing authenticated D1 anti-rollback check.

Display names, the optional 280-character bio, and profile avatar are ordinary server-visible profile metadata, not MLS content. The client center-crops and compresses an avatar to WebP before upload; the Worker accepts at most 128 KiB, stores exactly one content-addressed R2 object per account, and exposes it through a separate opaque immutable URL. Re-uploading identical bytes creates no object, while replacement/account deletion uses a D1 exact-key retry ledger and scheduled cleanup never lists the bucket. The first attempt uses one conditional provider-checksummed PUT. After an ambiguous response, the client retries once with identical bytes: committed D1 state returns without object access, while an unfinished write intent uses one exact metadata HEAD and skips the repeated PUT. That ledger also guards the short PUT-to-D1-commit window: routine GC ignores fresh intents, atomically leases each deletion, recovers an expired cleaner lease, and rechecks that a key is not the active avatar before deletion. A user cannot start a different avatar object while one prior write/cleanup remains unresolved, so an object-store deletion outage cannot grow unbounded avatar garbage. If the active object is missing or has inconsistent size/digest metadata, the first read opens a D1 repair circuit; later reads do not repeat the object-store GET, and reselecting the same local image restores the exact content-addressed key without changing quota or object count. Avatar bytes and the single object count against the same per-user quota as attachments and archives; no server thumbnail or historical-avatar object is retained. Profile changes emit lightweight durable sync hints to the account's devices and current shared-room peers. The full namespaced account ID remains visible beside profile data to reduce display-name ambiguity.

Dexie wraps only EdgeChat-owned auxiliary IndexedDB stores: the device-key vault, temporary device-history shards, local share/file-handler staging, and the small Web Push renewal record shared with the service worker. PGlite remains the sole owner of its OPFS/`idb://` data directory and is never inspected through Dexie. The tiny active-data-directory selector inside the PGlite worker and static service-worker writers use native IndexedDB with the exact same schema as their Dexie readers. Dexie is an API simplification, not encryption, and none of these local operations creates R2 traffic.

One browser installation may hold multiple local profiles, but only one is active at a time. Each profile has its own opaque UUID namespace for the bearer token, device-key/account-credential vault, PGlite/OPFS database, attachment and archive caches, restore hints, link-transfer staging, temporary backup/account-export files, and Push preference. Switching requires a successful current-draft flush before detaching the origin-wide Push subscription and reloading the selected namespace; a local write failure leaves the current profile active. Likewise, a primary tab denies ownership handoff instead of releasing the device-state lock when its final draft write fails. These operations do not fetch, upload, or copy history and create no R2/S3 traffic. Adding a profile creates an empty local namespace and does not contact the server until the user registers, logs in, links a device, or restores a backup. Explicitly removing a signed-in local profile deletes that profile's plaintext database, indexes, keys, credentials, caches, and staging without deleting the server account or another local profile. Because browser Web Locks and Web Push subscriptions are origin-wide, inactive profiles do not sync or receive notifications until selected. A startup failure never silently falls through to account creation or clears the active profile: a data-preserving recovery screen offers retry, profile switching, and authenticated encrypted-backup restore with a stable diagnostic code. Restore staging bypasses the current PGlite slot entirely, so even an unreadable active database can be replaced only after a new OPFS/IndexedDB slot passes decryption, schema migration, account binding and server anti-rollback checks.

The default onboarding asks only for a mutable display name. Before the first request, the client generates and durably stores independent 256-bit account and device credentials; the Worker generates the opaque `localpart` and globally namespaceable `user_id`, and persists only salted/hashed credential verifiers. If a timeout or gateway failure hides a committed response, the client waits briefly and automatically replays the byte-identical request once. The Worker returns the existing account only when both credentials and both original device public keys match, otherwise it fails closed; this cannot create another user, device, or object. The client never presents the account credential as a human password and includes it only inside an explicitly created encrypted portable backup or a target-device-encrypted linking envelope. Legacy/advanced password accounts remain accepted by the API, but are not the primary product path. The account credential authenticates account-level operations and a registered-device or checkpoint-bound restore, but it cannot enroll a fresh opaque-account endpoint: that endpoint must finish an existing-device-approved link. Per-device P-256 keys and MLS state remain the cryptographic chat identity, so possession of the account credential alone cannot decrypt or reconstruct lost history. Registration and its bounded retry use D1 only and create no R2/S3 traffic.

After initial authentication, an enrolled browser may recover an expired HTTP session with two device-held possession factors: its P-256 signing private key and a separate random device credential whose SHA-256 hash is stored in D1. The Worker issues a five-minute, one-time challenge only after validating that device credential; the device signs a canonical transcript binding the challenge, device ID, expiry and server domain. A failed proof, another device key, or replay cannot mint a session. The device credential is deliberately absent from portable identity export, rotates after authenticated backup restore, and is invalidated by relevant session termination. Account-credential transfer during device linking uses ephemeral P-256 ECDH, HKDF-SHA-256 and AES-256-GCM with a transcript binding the link and both device IDs. The target creates its own device credential before claim, persists it locally for lost-response retry, and signs a claim transcript binding both the session token and device-credential hashes to its device key. D1 commits the link transition, device credential and session together; a conflicting replay cannot replace either factor. Before claim, either the target's capability secret or an authenticated source account may hard-cancel the link. Cancellation rejects every later claim/room commit, removes exact temporary history keys, and durably schedules MLS Remove commits for rooms whose Add already landed; the source client also restores its persisted pre-Add MLS snapshot when the interrupted commit was never accepted. The small opaque account envelope and claim state are held in D1 until link cleanup; they create no R2/S3 object. Legacy password accounts may link without the account envelope, while opaque accounts fail closed until both the envelope and signed claim are complete.

Passkeys are an optional second server-login method, not an E2EE identity or recovery mechanism. Enrollment/removal requires the current account credential (automatically supplied by an opaque-account device, manually entered for a legacy password account), uses discoverable user-verified ES256 credentials, stores only the WebAuthn public key/counter/metadata in D1, and binds the user-chosen label to the one-time server challenge. Authentication deliberately accepts only an already registered, non-revoked device whose private keys remain in this browser; it cannot register a blank browser as a new chat device, restore MLS state, or recover plaintext history. A new endpoint must use the QR device-link flow or an authenticated encrypted backup. Unknown accounts and accounts without passkeys receive the same public option-response shape without allocating a challenge row. Five-minute challenges, scheduled cleanup, registration limits, per-target edge rate limiting, and all passkey operations use zero R2/S3 objects.

Anonymous authentication, appeal, device-link, restore-check, device-session, passkey, password-change, and Operator credential endpoints use Cloudflare edge rate-limit bindings with SHA-256-opaque target/IP keys; authenticated routes have a separate generous per-account ceiling. Edge counters are intentionally a fast, approximate PoP-local shield rather than an accounting source. Login also has an exact D1 backstop: ten failures in a rolling 15-minute window temporarily lock only an existing account, successful login clears the row, unknown identifiers never allocate rows, and stale rows are removed after 24 hours. Locked and invalid credentials return the same response, rate-limit logs contain only an event code, and these controls never read or write R2. Legacy password accounts can change their password only after re-entering the current one; generated opaque credentials cannot be manually changed into memorable passwords. The legacy change option atomically removes every other device's HTTP session, WebSocket ticket, Push subscription, device-session credential and outstanding challenge, then asks each room Durable Object to close that user's other device sockets; the current device remains online. This is session termination, not remote local-data erasure or MLS device revocation, and the UI says so explicitly. The account-appeal flow verifies the current account credential without storing it, accepts no free-form user narrative/contact data, and returns the same seven-day opaque receipt shape for invalid credentials and unknown accounts without allocating D1 state. Verified appeals store only category/status/timestamps plus a hashed receipt. Operators may approve or deny; an explicit login unlock is available only for an approved `login_locked` appeal and cannot reset credentials, restore a device, or access MLS state. Resolved appeal metadata and its internal operator action are removed after 30 days. Message requests retain their stricter hourly and outstanding limits. Production deployments still need a recovery design, independent crypto review, and formal MLS interoperability tests. The enforced CSP intentionally retains an `unsafe-eval` exception required by PGlite's PostgreSQL Wasm extension loader; application code must not use dynamic evaluation, and the exception should be removed when a compatible PGlite build exists.

## Personal notification bots

A bot is a restricted automation device owned by the current user, rather than a privileged server-side account. Provisioning `POST /api/v1/bots` returns its bearer token exactly once. The SDK generates its signing key, MLS credential, and KeyPackages locally, claims the owner's normal device KeyPackages, and creates one owner-only direct room. The owner-device KeyPackage claim is provisioning-only and is disabled as soon as that room is bound. After provisioning, the token is a `message:create` capability bound to that room: it may submit only encrypted text events and cannot create nested bots, enumerate or manage devices, change membership, submit receipts/control events, access other rooms, use archival/attachment administration, or mint a WebSocket ticket. The Worker applies a per-capability rate limit (60 messages/minute by default), while exact event-ID retries are not counted twice. Revoking the bot also revokes its device and token.

The result feels like an incoming webhook, while preserving the E2EE boundary: webhook handling runs in your own Node.js process and calls `sendText()`, which encrypts before making the EdgeChat request. Do not forward plaintext to a generic Worker webhook endpoint. Persist the returned state in a secret store; it contains the bearer token, signing private key, and MLS ratchet state, and must be saved after every send. Each signed event also carries a server-visible Bot ID/provenance marker. The Worker binds it to the presenting capability, rejects a missing or mismatched marker, and forbids ordinary user devices from claiming Bot provenance; the decrypted Bot label is accepted only when it matches that authorized ID.

```ts
import { PersonalBotClient } from "@edgechat/bot-sdk";

const bot = await PersonalBotClient.provision({
  baseUrl: "https://chat.example.com",
  userAccessToken: process.env.EDGECHAT_USER_TOKEN!, // needed only to provision
  displayName: "Builds",
  store: { async save(state) { await secrets.write("edgechat-builds", state); } },
});

await bot.sendText("Deployment finished");
```

On later starts, load the secret and call `PersonalBotClient.restore(state, { store })`. `sendText()` advances MLS, then saves the new MLS state together with the exact signed ciphertext envelope **before** starting the network request. If delivery is ambiguous, the envelope stays in the SDK outbox; call `flushPending()` after restart to retry the same event ID and ciphertext. A production integration should treat `BotStateStore.save()` as a durable, atomic secret-store write and should not acknowledge its upstream webhook until `sendText()` succeeds. Messages carry encrypted Bot origin metadata so the PWA renders them as incoming Bot notifications even though the device belongs to the same user. The current provisioning flow deliberately requires an existing user session; a QR/device-approval handoff can replace that credential transfer later without changing the protocol.

Bot text enters the same compacted room history as normal ciphertext; it does not create one R2 object per notification. Rate limiting therefore protects both D1 growth and eventual archive volume. Personal bots cannot upload attachments in this capability profile.

This integration still uses ACLs, but the policy is deliberately small. A bot token is an owner-created, revocable, expiring write capability for exactly one notification room and the `message:create` operation; it is not a general user session or a server-side webhook that can read conversations. This avoids room-invitation ACLs for a separate bot identity, not authorization itself.

## Saved messages

Choosing **保存** from a message menu creates one `purpose=saved` MLS room for the account on first use. It is a real encrypted room containing only that user, while all active devices are included as separate MLS members through their normal KeyPackages. D1 enforces one saved room per owner and the membership endpoint rejects additions or removals. The PWA labels it **已保存消息** and hides the save action while already inside it.

Saving text creates a normal encrypted event. Its MLS-encrypted payload carries a stable `room_id + message_id` source reference, so every device can jump from the saved copy back to the exact original when that room and message remain available locally. Ordinary forwarding deliberately omits this source location. If the original room is no longer accessible or its history is absent from the device, the saved copy remains readable and the client reports that limitation without issuing a speculative archive read.

Saving an image, voice note, or file uses the existing destination-scoped attachment grant: the saved event receives a new opaque attachment reference, but its grant points to the original ciphertext object. No second R2 upload, object, read, or storage-quota charge is created. Deleting the original message does not remove the underlying object while a saved/forwarded grant still references it.

## User blocking

Direct-user blocking is stored in D1 and enforced before user discovery, MLS KeyPackage claims, direct-room creation, new direct-room events, attachment uploads, and WebSocket admission. User discovery is deliberately directoryless: `/api/v1/users` accepts only one complete, canonical, same-server user ID. Nicknames, localparts, prefixes, remote-domain identifiers and the caller's own ID return an empty result rather than exposing an enumerable account directory. The valid path performs one exact D1 query whose joins exclude either direction of a block; it never reads or writes R2/S3. The PWA applies the same validation before issuing a request and directs people to exchange full IDs, contact links or QR codes. Display names and avatar references become visible only after that exact resolution. The account center exposes a keyset-paginated list of accounts the current user actively blocked, with an explicit unblock confirmation and direct-room reconnection; it never reveals accounts that blocked the current user. Users can choose whether everyone, only accounts with an existing accepted/shared room, or nobody may contact them. A previously unknown allowed account creates a reviewable direct-message request: it may submit exactly one encrypted `message.text`, cannot emit typing presence, and cannot upload attachments or archive segments until the recipient accepts. The inbox supports accept, reject, and report-and-block; reports expose only participant IDs, category, timing and an optional event ID—not plaintext. Request creation is limited to ten per account/hour and twenty outstanding requests. The same idempotent `room_id` reservation is charged before any target MLS KeyPackage is marked claimed, so repeatedly abandoning room creation cannot bypass the request budget or drain the target's package pool. Group creation requires an established relationship with every invitee so labeling spam as a group cannot bypass the request boundary. Adding a member is also rejected when any resulting member pair has blocked the other. These controls use D1/DO only before acceptance and create no R2 objects.

Existing ciphertext history and previously committed attachments remain readable to existing members: blocking cannot revoke plaintext or MLS state already delivered to another endpoint. Existing group rooms are not retroactively re-keyed by a personal block; removal from a group remains a separate MLS membership operation.

Inside a group, each account may hide another active member without changing membership or notifying that member. The preference is a small D1 row and a content-free `/sync` hint so all of the account's devices converge; it creates no room event and no R2 object. Every device still downloads, authenticates, decrypts, and advances MLS for the hidden sender, then keeps that decrypted projection locally so undoing the preference is immediate. PGlite excludes hidden senders from timeline paging, unread counts, reactions/receipts, text search, image semantic search, and typing presentation. This is a personal visibility control—not an ACL, cryptographic revocation, bandwidth reduction, or moderation action—and the server necessarily sees the room/user preference IDs.

## Identity, devices, and rooms

- Users: `@alice:example.com`
- Rooms: `!opaque-random-id:example.com`
- Devices: opaque UUIDs with independent signing and ECDH key pairs
- Events: `$opaque-random-id:example.com`
- Logical messages: the initial event ID, stable across future edits/reactions
- Message parts and attachments: independent opaque IDs scoped through the logical message

`SERVER_NAME` is part of every user, room, and event ID from day one. Phase 1's `LocalFederationTransport` rejects IDs whose domain is not local. The Worker applies the same canonical/local event-ID check before both normal ordering and client-assisted history repair, so an accepted event can always be used as a globally scoped logical-message reference. A room belongs to exactly one home server and one Durable Object. Room events are a linear stream (`1, 2, 3…`), not a DAG. Rejected identifiers create no D1 event row, Durable Object state, or R2 operation.

Each browser device owns an Ed25519 MLS credential and a pool of one-time X25519 KeyPackages. Room creation consumes one KeyPackage for every other active device, creates an MLS group locally, and stores the resulting Welcome plus public ratchet tree as that device's onboarding packet. The founder retains its secret tree only in the local vault.

The PWA checks its own KeyPackage pool at startup, every 30 minutes and when returning to the foreground. Below eight available packages it generates enough to reach a target of 24, saves the new private MLS state to IndexedDB first, and only then publishes the public packages. D1 fingerprints new packages for upload deduplication and caps active packages at 64 per device. Claims are bound to the future namespaced `room_id`: retrying the same room returns the same reservation, while another room cannot reuse that one-time package. Abandoned claims expire after 24 hours and consumed rows after seven days. This lifecycle uses D1 only and creates no R2 objects.

Application messages are MLS PrivateMessages. Add/remove operations create an MLS Commit, advance exactly one epoch, and are carried as signed control events. A member-add claim returns only the invitee's active user devices and binds one fresh KeyPackage per device to that room. The signed Commit covers the action, target user, and exact target-device set; the Worker requires matching Welcome recipients and one-time claim IDs before it orders the event, consumes the claims, and changes membership. An exact signed-envelope retry is idempotent, while reusing its event ID with a different signature is rejected. The SolidJS group settings expose these operations only to the owner. Before publishing, the PWA stores the exact signed Commit, Welcome inputs, and pre/post-Commit MLS snapshots in a dedicated PGlite outbox; startup and reconnect resume that same operation, and a stale epoch safely restores the pre-Commit snapshot before retry is offered. Existing members process the Commit; newly added devices join from Welcome. This ordinary membership path uses local storage, D1 and the Room Durable Object only and creates no R2 object.

A non-owner leaves through a two-stage request because an MLS member cannot safely author the Commit that removes its own leaf. D1 durably records the request and emits content-free sync/Push hints; the member becomes read-only while any current owner device uses the same crash-resumable membership outbox to publish the signed Remove Commit. The signed envelope binds the leave-request ID, so cancellation wins if the delegated Commit has not already been accepted. Completion removes the member's per-device onboarding packets and closes its room access. A group owner first chooses an active successor in group settings: the PWA queues an MLS-encrypted, signed `control.owner.transfer` event, while RoomDO serializes the event and atomically swaps its authoritative owner before D1 is reconciled. Exact-envelope retries remain idempotent, concurrent actions from the former owner are rejected, and the former owner can then use the ordinary leave flow. Leave requests, ownership transfer and membership control use D1, Durable Objects, local state and Push only—no R2 read, write, list, or object.

Group names are MLS-encrypted from creation onward. The room-creation request always carries `name: null`, and the Worker rejects any plaintext group name before allocating room or object-storage state. After the nameless room is established, the owner immediately queues its chosen name as a normal `control.room.profile` event; later profile changes use the same path. The same encrypted profile can contain one client-cropped WebP group avatar: its key, nonce, media metadata, and an at-most 8 KiB client-generated preview remain inside MLS ciphertext, while the Worker sees only the opaque attachment transition needed for authorization and exact-key reclamation. Profiles are projected by authoritative sequence into PGlite instead of mutating server room metadata. After adding a member, the owner re-emits the current encrypted profile at the new MLS epoch so the new endpoint can receive it without pre-join history. Name-only updates reuse the current avatar object, replacement schedules the previous exact object for deletion, and removal does not scan R2. Conversation lists and headers render the encrypted event preview without an object GET; explicitly opening group settings may upgrade to the OPFS-first original. The active original is protected from retention GC. Thus a group consumes at most one current avatar object, with no separate thumbnail object or retained versions. Personal-bot room labels remain ordinary server-visible integration metadata.

Removing a user closes its room sockets after the removal Commit is durably ordered. Removing another device is an explicit, resumable two-phase operation: D1 records every affected room and reserves its next epoch, the PWA stores each exact signed `control.device.revoke` Commit in a local PGlite outbox before persisting the advanced MLS state, and the Worker revokes sessions, Push state and outstanding WebSocket tickets only after every room Commit is durably ordered. The Room Durable Objects then close all live or hibernated sockets whose serialized attachment identifies that device. Partial progress stays visible and can be retried after reload. Normal ciphertext events must match the room's current epoch, so a removed device cannot receive a late event encrypted for the old epoch. An opaque account credential retained on that endpoint does not let it re-register the revoked device or create a replacement device; another active device must approve a distinct link. This revocation workflow uses D1, Durable Objects and local storage only; it creates no R2 objects. A newly added device does not receive historical MLS epoch secrets automatically.

The device-link protocol adds a genuinely distinct endpoint instead of cloning the old device identity. The new endpoint creates its own WebCrypto identity, OpenMLS client, and one-time KeyPackages, then receives an unguessable 15-minute link ID plus secret. The SolidJS setup screen renders that capability as a QR code whose secret stays in the URL fragment. An authenticated existing device scans it with the browser camera or pastes it, compares eight groups of canonical public-key fingerprint characters, and must explicitly approve. Approval extends the capability to a hard 24-hour completion window, which the target persists locally across reloads. D1 then reserves one MLS-add task per active room; an active existing device submits a signed `control.device.add` Commit and the new endpoint receives only its MLS Welcome/public ratchet tree. Both sides persist their exact progress locally: the approving endpoint records the signed event, pre/post-Commit OpenMLS snapshots, and Welcome packet in PGlite before network submission, while the new endpoint saves its identity, KeyPackage state, link secret, client-generated session token and independent device credential before publishing them. Reloads therefore retry the same signed claim rather than creating a second commit or rotating either credential after an ambiguous response. A session is issued only after all rooms complete and the new endpoint signs a transcript binding both credential hashes to its device key; the global opaque account credential cannot bypass this final claim. An unclaimed link becomes unusable at its deadline even if every MLS Add already completed: the Worker deletes its exact temporary history keys, stages durable MLS Remove work for rooms it entered, and wakes another active device to finish those commits. A link with no joined rooms is revoked immediately. This expiry path uses no bucket listing or object metadata probe, and the ordinary successful path gains no R2/S3 request.

Peer identity verification is device-level rather than a single user-level checkbox. From a conversation, a user can compare each active member device's stable signing-plus-encryption-key fingerprint over a separate trusted channel and explicitly mark that exact fingerprint as verified. The conversation header shows complete, partial, or changed-key state; a new device starts unverified, and a different fingerprint under a previously verified device ID produces a prominent warning instead of inheriting trust. Users can expose their own per-device fingerprints from the account panel. Verification rows remain in local PGlite, are included only in user-initiated encrypted backup or authenticated linked-device history transfer, and are never uploaded as a server trust graph. Opening or updating verification performs one room-scoped D1 device-key read and no R2/S3 operation. This detects key substitution when users actually compare through an independent channel; it does not protect a compromised endpoint or a comparison performed through the same compromised service.

To restore history without copying pre-join MLS secrets, the approving device creates one versioned history bundle containing a gzip PGlite snapshot plus its OPFS attachment and archive-segment ciphertext caches. The database contains locally indexed plaintext, search data, attachment metadata, and archive segment keys; object bodies remain ciphertext and their keys remain inside E2EE message payloads or the local database. The client persists the bundle locally, splits it into 16 MiB plaintext shards, and derives device-to-device keys from the two devices' P-256 ECDH identities with HKDF. Every shard is independently encrypted in authenticated 1 MiB AES-GCM records and bound to the link, transfer, source, target, and shard index. The client also pins the final ciphertext SHA-256; the Worker streams each opaque shard directly to R2/S3 with provider checksum verification, charges it to the normal storage ledger, and never receives a plaintext snapshot, attachment manifest, or room key. D1 is the authoritative transfer manifest and resume cursor. The former single-object history endpoint is intentionally absent: only manifest plus independently authenticated shard routes are accepted, so no client can bypass bounded/resumable transfer with one large object.

After every MLS Add completes, the new device downloads only missing shards. It authenticates and decrypts each shard, durably stages that plaintext shard in a device-local IndexedDB transfer area, and only then acknowledges exact-key R2 deletion and immediate quota return. A reload resumes from locally staged and remotely ready shard indexes; the target cannot claim its session until every declared shard is durably staged and acknowledged, so a successful claim leaves no temporary history object or quota charge behind. The source cannot create or upload a transfer after claim. It retains the exact locally staged snapshot and manifest until a durable `device.link.claimed` event confirms that claim. If the target's first GET finds a missing object or invalid provider metadata, D1 circuit-breaks that shard, emits a content-free repair event, and prevents subsequent retries from reading the same bad object. The source then re-encrypts the original shard index from that retained snapshot and replaces the exact temporary key; it never reconstructs a different snapshot under the existing manifest. After all shards arrive, the PWA atomically imports a sanitized PGlite database and restores attachment and archive-segment ciphertext to their own OPFS caches. It then acknowledges still-live canonical objects as GC-safe local copies; an intentionally collected segment stays local without being recreated remotely. Cron removes abandoned ready shards by their exact D1 keys without bucket listing. The healthy request cost is one PUT, one GET, and one DELETE per 16 MiB bundle shard—not per room, message, attachment, or segment—so a 1 GiB bundle uses about 64 temporary objects while it is transferred. A missing or corrupt shard costs at most one failed GET per repair episode; a missing row returns quota immediately, while corrupt ciphertext is exact-key deleted before replacement. If a PUT response is lost, the retry reuses identical bytes and the pinned digest: a committed D1 row costs no object call, while the post-PUT/pre-D1 window uses one exact HEAD and skips the second body transfer. It never uses GET/LIST for upload recovery.

The OpenMLS provider storage—including private KeyPackage material, secret trees and past-epoch state—is exported as a device snapshot and stored with the browser device keys in IndexedDB. It is restored into Wasm on reload and persisted after every MLS mutation. While a device removal is pending, PGlite also holds a transient post-Commit snapshot beside the exact signed Commit so a crash between its two local persistence steps is recoverable. That snapshot is secret endpoint material and is deleted with the revocation outbox row after server acknowledgement; it leaves the browser only inside an explicitly created encrypted portable backup.

## Sync, references, and local search

The PWA stores its monotonic global cursor in PGlite. `/sync` pages through a D1 log scoped to the authenticated user. Events are decrypted and inserted idempotently into the local database; a generated PostgreSQL `tsvector`/GIN index provides local text search, with a substring fallback useful for CJK queries. The search field updates its visible state immediately but coalesces rapid input for 180 ms, suppresses queries during IME composition, invalidates in-flight results as soon as newer text arrives, and cancels pending work when the dialog closes. Clearing the field remains immediate. This avoids queuing a local substring scan for every composition keystroke without adding another plaintext index or any HTTP, D1, R2, or S3 operation.

Incoming MLS transitions are crash-recoverable across the browser's two local storage systems. Before advancing the durable device vault, the client writes the signed envelope, decrypted payload, and exact pre/post-transition MLS snapshots into one profile-scoped PGlite staging row. Startup verifies that the current MLS snapshot equals one side of that transition, advances it to the authenticated post-state when necessary, then idempotently rebuilds the message/relation projection before deleting the row. Local persistence failures remain retryable and are never mislabeled as malformed sender content. Staging is endpoint-secret plaintext state, is cleared with the profile, and creates no HTTP, D1, R2, or S3 operation.

Opening an old text or image search result reads a bounded, contiguous window around its room sequence directly from PGlite instead of assuming the message is among the latest 200 rows. The timeline enters an explicit historical-view state, keeps live sync writing to the local database without replacing the reader's context, and offers a persistent “back to latest” action. New arrivals are not marked read merely because that room remains selected while the user is inspecting old context. Stale asynchronous navigation is discarded after another result or room is selected. This path performs no network, D1, or R2 operation.

Each conversation also exposes a device-local media library for images, voice notes, and files. It keyset-pages the normalized PGlite attachment projection by room sequence and part position, omits retracted messages and locally hidden group members, and navigates through the stable source `message_id`. Image tiles prefer the sender-generated thumbnail carried inside the MLS-encrypted message, then upgrade from ciphertext already present in that profile's OPFS cache; opening the library never downloads a missing original, lists the bucket, or issues an R2 request. A message without a valid bounded thumbnail remains a placeholder, and choosing the item returns to its message where the explicit attachment path may perform one authorized, single-flight read. The library reports incomplete local-history coverage instead of presenting its results as a complete server catalog.

MLS authentication proves which room member authored a payload; it does not make that member's decrypted fields trusted application input. Before an incoming message is projected into PGlite, the PWA binds its logical message ID to the signed event ID and bounds or normalizes part IDs, text, reply/quote references, saved-message backlinks, Bot origin, contact cards, filenames, MIME types, dimensions, durations, attachment keys/nonces, attachment count, and total declared plaintext size. Reply/quote references must stay in the current room, while `message.text`, `message.file`, and `message.contact` must contain only their permitted part shapes. The ordered attachment IDs inside the encrypted payload must exactly match the opaque attachment references already authorized by the Worker. A mismatch quarantines the event before local projection, attachment decryption, rendering, or semantic indexing. Large images that exceed the local preview policy remain ordinary downloadable files; merely rendering them performs no R2 read and no image decode.

An already authenticated device can open while the server is unreachable. PGlite keeps a validated, device-bound session summary and complete room-list snapshots alongside local messages; the summary deliberately excludes the bearer token, account/device credentials and private keys. Its dedicated Worker reports progress while loading the runtime, opening OPFS/IndexedDB, and applying local schema migrations. Each phase refreshes a 60-second inactivity watchdog, while an independent 180-second absolute bound still terminates a genuinely wedged Worker; slow dual-device startup therefore does not repeatedly discard healthy PGlite work. Offline sends enter the existing ciphertext outbox. JSON GETs such as discovery, room lists and sync metadata receive at most one 250 ms-delayed retry after a network, gateway, `408`, or `425` failure; deterministic 4xx responses and 30-second client timeouts are not replayed. Attachment bodies, device-history bundles and archive Range reads use a separate binary response path and are deliberately excluded, so this convenience cannot multiply an R2/S3 GET. When connectivity returns, one serialized `/sync` catch-up advances the durable cursor before desired room WebSockets reconnect, then the room list is revalidated against the server. Returning a suspended PWA to the foreground also performs durable catch-up while probing every apparently open room socket with the existing ephemeral RoomDO ping. Responsive sockets remain in place; only a socket that misses the three-second reply is replaced, after which the local outbox resumes. The heartbeat writes no room event, D1 row, archive input, or R2/S3 object. Concurrent catch-up and foreground-resume calls share one task so an older response cannot regress the cursor or duplicate socket churn, and an enqueue racing the end of an empty outbox scan forces another drain. Membership removal, device revocation, credential-driven session termination and account deletion socket codes are terminal rather than consuming endless reconnect/D1 requests. A normal 30-day session expiry preserves local history and reauthenticates with the device-held credential; explicit device revocation follows the existing local key/cache cleanup path. Indexed daily GC removes at most 500 expired bearer sessions and 500 unconsumed one-minute WebSocket tickets per run, reclaiming routine lost-response and abandoned-reconnect residue without turning cleanup into an unbounded mutation. None of this recovery or cleanup path reads or writes R2.

Only one page per browser origin may open the device's PGlite and OpenMLS state. Before constructing the application, the entry point takes one origin-scoped exclusive Web Lock; additional tabs remain in a database-free standby screen and automatically start only after the owner closes or safely hands off. An explicit handoff stops typing, flushes the text draft, refuses transfer while MLS, sync, outbox, archive, recovery, retention, media, device or account work is in flight, then closes new admissions and waits for already-admitted durable writes before releasing the lock. A timed-out requester cancels preparation so the old page cannot silently quiesce after retaining ownership. Browsers without the required safe locking primitive fail closed instead of running two MLS ratchets. This coordination is entirely local and produces no additional HTTP, D1, WebSocket, or R2 traffic.

Outgoing messages are written to a PGlite outbox as one immutable signed MLS ciphertext envelope before the network request begins. Network failures retry that exact envelope with exponential backoff, so the Room Durable Object can deduplicate by `event_id` without advancing the MLS sender ratchet twice. The item leaves the outbox only after the server response has been committed into the local message database. Pending, retrying and permanent-failure states remain visible beside the corresponding bubble and survive reloads.

Every protocol event has an immutable `event_id`. Every visible message has a stable `message_id`; the initial event uses the same ID, while future edit, reaction, reply, quote, or tombstone events reference that logical ID inside MLS ciphertext. A versioned message payload contains independently identified text/image/file parts. Room sequence numbers are ordering cursors and must never be used as durable references. The client revalidates the complete ordered ciphertext envelope before any sync, WebSocket, archive, peer-recovery, or staged event reaches crypto or local storage. It pins each room device's P-256 signing key in PGlite, verifies the outer event signature, and requires the sender identity authenticated by OpenMLS to equal the signed `device_id` before advancing durable MLS state. Revoked historical device keys remain available for old ciphertext verification but are never archive-key recipients. Sender outbox projection additionally requires the server's accepted event to be byte-for-byte identical to the original signed envelope; only `seq` and an internally bound acceptance receipt may be added.

When remote retention has already collected a bounded event gap, another device may relay up to 500 signed ciphertext events in one zstd-compressed, device-to-device authenticated recovery bundle. The source computes a ciphertext SHA-256 once; the Worker binds it to D1 and portable object metadata, verifies it through the R2/S3 provider checksum, and uses a conditional PUT. A lost success response is retried with identical bytes: an already committed D1 row returns without touching object storage, while a staged object is reconciled by one exact-key HEAD. No recovery path performs a bucket LIST or creates one object per message. The target verifies the stored size and digest metadata before decrypting, then acknowledgement deletes that exact temporary object.

Replies keep their target reference inside the encrypted message payload and render a local sender/text preview with jump-to-message behavior. A user can also quote a whole text message or a browser-selected substring: the client stores a bounded 2,000-character author/text snapshot plus the stable target reference inside the new MLS ciphertext. The snapshot keeps the quote meaningful when the original is not locally indexed, while the target still supports navigation and attribution from local evidence. A quote is newly authored copied content; retracting or later editing the source does not rewrite that already-delivered snapshot. Quote text is not added to the new message's FTS body, creates no attachment, and performs no R2 operation.

Text edits and reactions are immutable encrypted relation events rather than mutations of the original event. The local projection applies the newest valid sender edit, preserves attachment and part IDs, rebuilds FTS content, and marks the message as edited. Reaction state reduces each user's ordered reaction stream to its latest value; `null` removes that user's reaction. Both projections tolerate relation events arriving before their target. Failed relation sends remain in the same durable outbox with an explicit retry state. These small events are packed into normal archive segments and create no dedicated R2 objects.

Read positions are MLS-encrypted `receipt.read` events. The server observes that a receipt event exists, its sender, room and timing, but not the `up_to_seq` value. The PWA maintains per-room read state and unread counts in PGlite, coalesces foreground progress for 750 ms, and sends only when the highest visible message sequence advances. Other members' monotonically increasing positions drive “已读” indicators locally. Sending read receipts is a device-local preference: disabling it pauses the outbox, lets an already-sending event settle, removes every unsent read receipt without touching ordinary messages, and prevents new receipts. Already delivered receipts cannot be withdrawn. Delivery receipts remain enabled because they represent durable transport recovery rather than a user reading the message.

Conversation organization is intentionally cheap. Pinning, archiving, and “mark unread” reminders live only in the current profile's PGlite database. A manual unread reminder raises the local badge without rewinding the monotonic read position or retracting an already-sent receipt; opening or explicitly marking the conversation read clears it. Notification mute is device-scoped D1 metadata and supports one hour, eight hours, one week, or indefinite duration. It controls only content-free Push delivery and never creates a room event, archive input, attachment, or R2/S3 operation.

Delivery positions are separate MLS-encrypted `receipt.delivered` events generated only after an incoming visible message has been decrypted and committed to local PGlite. They are coalesced per room, persisted through the normal outbox, recovered after reload by comparing local incoming history with the last accepted receipt, and reduced per user so multiple devices do not inflate group counts. If an incoming or outgoing MLS projection is in its crash-safe commit window, a racing background receipt waits through five bounded exponential-backoff attempts instead of surfacing the expected safety barrier as a send failure; later sync or message activity still reconciles an unsent receipt from monotonic local state. Outgoing bubbles distinguish “已发送” (server accepted), “已送达” (at least one recipient endpoint stored it), and “已读”. Both receipt types are hidden from the timeline and packed into ordinary archive segments, so they create no dedicated R2 objects.

Typing presence is deliberately not a room event. When its device-local preference is enabled, the composer sends a bounded `{type:"typing", active}` frame over its authenticated room WebSocket; disabling it immediately sends one stop frame for an active indicator and prevents later start frames. The Room Durable Object derives the sender from the hibernation attachment and broadcasts a six-second, connection-scoped indicator. Clients aggregate multiple devices by user and expire missing stop frames locally. Start frames refresh at most every 2.5 seconds and stop after four seconds of inactivity. The HTTP event endpoint rejects `typing.start` and `typing.stop`, so typing creates no sequence numbers, D1 sync rows, archive input, or R2 objects. This is presence metadata rather than E2EE content: while enabled, the server and current room members can observe who is typing and when.

General online presence is a separate device-local setting and is off by default. When enabled, that device adds an explicit opt-in to its existing authenticated room WebSockets. RoomDO derives the identity from the trusted socket attachment, aggregates multiple connections/devices into one active user per room, sends a bounded snapshot on connect, and emits offline only after the user's last sharing connection leaves. Pending stranger-message requests never receive or contribute presence, and clients exclude the current user, non-members, and locally hidden group members. Presence is deliberately ephemeral: there is no `last_seen`, D1 row, sync-log item, room event, Push payload, archive segment, or R2/S3 object. A missing indicator means only that no currently connected device is sharing presence; it is not proof that the person is offline.

Pinned and archived chat state is device-local PGlite data. Pinned chats sort ahead of the normal server order; archived chats move to an explicit, reversible archive view. A visible message from another user automatically restores an archived chat unless it is muted. Muting is also mirrored as one `(device_id, room_id, muted_until)` D1 row because Web Push currently uses an empty, content-free payload and the service worker cannot identify the room. The push recipient query excludes active mute rows before contacting the provider. These preferences never enter the room event stream or an archive segment and create no R2 objects; the server necessarily learns that a particular device muted a room and the expiry time.

Unsent text drafts are written to local PGlite first. The client debounces local writes, restores plain/reply/quote/edit composition without overwriting input typed during an asynchronous restore, and clears a draft only after the outgoing event is durably queued. With multiple active user devices, a separate two-second quiet-period outbox encrypts the draft—or an indistinguishable deletion tombstone—independently to every device using ephemeral P-256 ECDH, HKDF-SHA-256 and AES-256-GCM, then signs each envelope with the source device. D1 retains at most one current opaque envelope per room and target device; `/sync` carries only a content-free update hint. Stale client timestamps cannot replace newer server envelopes, revoked targets are removed, and changed device sets re-encrypt active drafts after linking. Draft sync creates no room event, archive input, WebSocket frame, Push payload, or R2/S3 object. The server can still observe the room and source/target device IDs, update timing, and ciphertext size. Portable backup retains local drafts; linked-device database transfer strips them because the new device obtains its own addressed envelope after activation.

Each conversation can also keep decrypted history on the current device forever or for 90, 30, 7, or 1 day. Saving a finite policy atomically records the preference, removes already expired message rows, plaintext FTS content, normalized parts, local attachment metadata, edit/reaction projections, and image embeddings, and queues the affected opaque attachment IDs for device-local OPFS reclamation in that same PGlite transaction. A bounded foreground drainer deletes only those exact ciphertext-cache keys; a crash or blocked file handle leaves durable retry work instead of orphaning browser storage, and one failed key cannot prevent later keys from being reclaimed. The durable sync cursor, processed-event ledger, and small sender-retraction tombstones remain, so normal `/sync` does not recreate purged plaintext and later historical indexing cannot resurrect a withdrawn message. Startup, foreground return, and a six-hour timer enforce the policy. This setting is intentionally device-local: it neither deletes another participant's copy nor promises recovery, and its database and cache cleanup performs no HTTP, D1, R2, or S3 request. Remote ciphertext and committed attachment objects remain subject to the normal sender-retraction and account-deletion lifecycles, so local retention does not reduce cloud quota.

An explicit destructive action can clear a conversation's currently accepted history from one device immediately. One transaction first advances a monotonic `cleared_through_seq` floor, records exact OPFS attachment and fully covered archive-segment cache keys in the durable local cleanup queue, then removes message plaintext, FTS/semantic projections, normalized parts, attachment metadata, relation rows, signed repair envelopes and local archive keys/metadata through that sequence. This floor prevents a later archive lookup, delayed projection or peer-history import from silently recreating cleared content while allowing newer events and MLS state progression to continue. Read state advances without emitting a receipt, manual-unread state clears, and the bounded foreground drainer reclaims those exact ciphertext-cache keys even after a reload. Drafts and pending sends are not discarded; clearing is refused while a visible message is still in the outbox or the room needs history recovery. The action never requests or deletes a cloud object, so other devices and administrator-retained ciphertext remain unchanged and its R2/S3 operation count is zero.

The conversation settings can stream the currently indexed, non-hidden local history into a human-readable UTF-8 transcript. The export preserves chronological order and stable message IDs, labels edits, forwards, quotes, contacts, retractions and encrypted personal-Bot attribution, but deliberately omits ciphertext, attachment keys/nonces and attachment bodies. A native save handle is used when available; otherwise the PWA writes through profile-scoped OPFS staging before download, with a bounded 64 MiB whole-Blob fallback. The user can cancel between bounded 500-message pages, and interrupted staging is deleted exactly. This is an explicit plaintext export and is labelled accordingly. It performs no Worker, D1, R2 or S3 request; users who need recoverable application state rather than a readable transcript should use the authenticated encrypted backup.

A separate per-conversation “new messages disappear” policy is an MLS-encrypted `control.message-expiry` event. Its room sequence is the boundary, so changing the timer never retroactively deletes older messages; the encrypted duration is applied only to later visible messages. Each device derives the same deadline from the server-signed acceptance time (falling back to the signed creation time for imported legacy envelopes), then removes the local plaintext row, FTS entry, normalized parts, attachment metadata, edit/reaction projections, and image embedding while transactionally queueing exact local attachment-cache reclamation. A compact expired-message tombstone prevents later sync, archive indexing, edits, or reactions from recreating that local plaintext, while the exact signed ciphertext envelope remains available for authorized peer repair. Enforcement runs at startup, foreground return, and every 30 seconds. The server can see that a policy control event occurred, its sender, room, sequence, timing, and ciphertext size, but not the selected duration. This is cooperative endpoint deletion: it cannot prevent screenshots, forwarding, export, backups, or a modified client from retaining content. Cloud ciphertext follows the administrator's independent retention/GC policy.

The expiry control event and all expiring messages use the existing D1/RoomDO event path and normal multi-message archive compaction. They create no per-message or per-policy R2/S3 object, and local expiry performs no network request. Local OPFS ciphertext for the expired projection is reclaimed by exact cache ID; the canonical cloud attachment object is not eagerly deleted merely because one local message expires, because it can still be referenced by another message or device and remains governed by reference-counted server GC.

Malformed application events are retained in a local quarantine table and marked processed so one authenticated but buggy or malicious sender cannot permanently block later sync. A failed membership Commit is deliberately not skipped because later MLS epochs would no longer be trustworthy.

Deleting a message creates a separately signed and MLS-encrypted `message.delete` tombstone. The Worker sees only its opaque target event ID and permits deletion only when the authenticated user sent the target. Clients replace content with a tombstone, clear plaintext full-text entries, remove attachment metadata and discard local image embeddings. Tombstones also work when history is indexed out of order: they are retained separately and applied if the target arrives later. This is sender-controlled retraction, not a promise that recipients did not already save or export plaintext.

Image data, message rows, content parts, attachment metadata, and semantic vectors use separate tables because their retention and reindexing lifecycles differ. Decrypted images are embedded in a dedicated browser Worker using quantized CLIP encoders; vectors are normalized and stored by `attachment_id + model_id + model_version + preprocessing_version`. Text queries use the matching text encoder and cosine similarity is calculated locally. Neither embeddings nor queries leave the device.

Voice notes are recorded through the browser MediaRecorder API, preferring Opus containers when available and otherwise allowing the browser's native audio encoding. Recording is capped at ten minutes and 25 MiB, can be cancelled before send, and is encrypted through the same client-only attachment path as files. The encrypted filename, MIME type, duration, key and nonce remain inside the MLS payload. R2 receives one opaque ciphertext object: no waveform, server transcoding, codec variant, or thumbnail object is created. The timeline performs no audio GET until the user explicitly plays or saves the note; saving an already decrypted note reuses its in-memory Blob rather than reading R2 again. Forwarding creates only a destination-scoped D1 alias to the existing object.

The semantic runtime is loaded on demand. The current default downloads separate q8 text and vision encoders (approximately 62 MB and 89 MB) and an ONNX WebAssembly runtime on first use, then relies on browser caches. The provider boundary and versioned index allow a deployment to self-host or replace the model without changing message storage. The default CLIP checkpoint is English-focused; production deployments requiring strong Chinese-language image retrieval should select and validate a compatible multilingual image/text model rather than mixing vectors from different models.

Coverage is tracked per room (`oldest_local_seq`, `newest_local_seq`, `indexed_until_seq`, `history_complete`). Search results can therefore distinguish locally indexed history from history that has not been downloaded yet.

The database runs in a dedicated worker. Each local profile prefers its own `opfs-ahp://edgechat-local-<profile UUID>` directory; browsers without the required OPFS worker support fall back to the equivalently isolated `idb://` slot.

## Archive format

R2 never stores one object per message. `packages/sync/src/archive.ts` implements a range-decodable binary segment:

```text
40-byte public framing header
device-wrapped segment-key envelope
encrypted authenticated index
encrypted compressed chunk 0
encrypted compressed chunk 1
...
```

The encrypted index maps message sequence to chunk, relative data offset, encrypted length, and original length. Segment format v3 compresses every 64–256 KiB target chunk independently as a standard Zstandard frame using the `@paddor/zrip` Rust/Wasm codec, then derives a distinct AES-GCM key using HKDF and its chunk number, uses a random nonce, and authenticates `room_id + segment_id + chunk_index` as AAD. The segment key is independently wrapped to every active room device with ephemeral P-256 ECDH, HKDF-SHA-256, and AES-GCM; the transcript binds room, segment, exact sequence range, and recipient device. An offline device can therefore open an archived segment directly with its device key before advancing MLS, rather than depending on a key event from a later MLS epoch. The server sees recipient device IDs, the ephemeral public key, and opaque wraps, but never the segment key. The header records bounded envelope and index sizes; each descriptor records a bounded chunk size, so hostile data cannot request an unbounded allocation. A client fetches only the header, the coalesced key-envelope/encrypted-index range, and required chunk ranges. Exact concurrent Range reads are single-flighted. After successful authentication, immutable framing/envelope/index bytes are cached in that profile's PGlite database, while independently authenticated chunks up to 512 KiB share a bounded 8 MiB ciphertext-only session LRU; repeated search/catch-up over the same chunk therefore avoids another object request. Failed, unauthenticated, or discontinuous chunks are never cached and Range failures are not automatically retried. If an exact complete segment already exists in the profile's OPFS cache—because this device compacted it or received it during device linking—the reader authenticates and reads that local copy without any R2 request. A corrupt or size-mismatched local copy is evicted and retried through bounded Range requests. Authentication failure always aborts before decompression.

Compression is deliberately limited to historical archive chunks. Live MLS application messages and encrypted attachments are not compressed by the server: the server never sees their plaintext, and many attachment formats are already compressed. This also avoids mixing attacker-controlled and secret plaintext in an online compression context.

Attachments use one version-2 encrypted object rather than one object per message chunk. A 40-byte public framing prefix locates an encrypted, strict Valibot-validated manifest; files up to 1 MiB use one authenticated record and larger files use independently authenticated 256 KiB AES-256-GCM records. HKDF-SHA-256 derives a separate key for the manifest and every chunk, and AAD binds the random MLS-protected attachment context, chunk number, exact plaintext length, and total size. Clients can therefore request the prefix, manifest, and only the contiguous ciphertext chunks needed for a plaintext range. The Worker streams exact `Range` requests to R2 or S3/B2 without seeing filenames, MIME types, keys, manifest contents, or plaintext. Zero-copy saved/forwarded attachments remain valid when their ACL grant receives a new opaque server locator because that locator is intentionally not the cryptographic identity.

Every committed attachment or archive segment is charged to a D1-backed per-user storage ledger before the object-store write. The default hard limits are 2 GiB and 100,000 objects per user and can be changed with `USER_OBJECT_QUOTA_BYTES` and `USER_OBJECT_LIMIT`; `GET /api/v1/storage` reports the split between attachments and archives. The browser computes the encrypted attachment's SHA-256, chooses a 192-bit opaque attachment ID before networking, and records that ID in the current message attempt before sending both with the fixed-size body. The Worker binds that ID in D1 to the uploader, room, length and digest, relays the body through a `FixedLengthStream`, and requires the selected provider to verify the signed payload digest while writing. A normal upload is one conditional object PUT without buffering the complete ciphertext in Worker memory or adding a discovery HEAD/LIST. A timeout or lost response retries once with the same ID: if D1 committed, the Worker answers from D1 with zero object-store operations. If the Worker stopped after the object PUT but before D1 finalization, the retry performs one create-if-absent PUT and at most one exact-key HEAD, verifies all bound metadata, and finalizes the existing quota reservation instead of writing a duplicate object. If both responses are lost or a later message step fails, the client cancels the exact pre-recorded ID. D1 marks an in-flight claim cancelled before issuing one exact-key DELETE; a late PUT rechecks the claim and deletes its own object, so neither race can resurrect a live attachment or wait for the orphan sweep. Cancellation never uses HEAD or LIST. S3/B2 cleanup batches up to 1,000 exact keys into one `DeleteObjects` call whose bounded XML body carries both SigV4 SHA-256 and the API-required `Content-MD5`; computing those hashes locally adds no provider request. Pre-object failures release the reservation; post-object failures retain their bounded write intent for retry, exact cancellation, or exact-key cron cleanup. The checksum and client ID are mandatory because there is no pre-deployment legacy-client contract. To limit object and Range-request amplification, low-volume rooms wait for 1 MiB of archive input or 500 events before creating a segment. See [the maturity and storage roadmap](docs/MATURITY_ROADMAP.md).

An attachment upload starts as uncommitted. Before the first PUT for a message, the PWA journals all of its preallocated opaque attachment IDs in PGlite. Durable outgoing MLS staging/outbox/message evidence suppresses cleanup; without that evidence, caught failures and startup/reconnect recovery issue one bounded batch abandonment and retain the journal while offline. This closes the page-crash window without LIST/HEAD/GET or an extra PUT. The signed message envelope exposes only its opaque attachment ID; after the room event is durably ordered, D1 binds the object to that event. A daily Worker cron remains the seven-day backstop for uncommitted ciphertext and atomically returns its bytes/object count to the owner's quota. A valid sender tombstone creates a durable deletion job: the R2 object is deleted first, then D1 removes its metadata and returns bytes/object count in one batch. Failed object deletion remains queued for the cron, and idempotent tombstone retries cannot decrement quota twice. Packed message segments are not rewritten for a single tombstone because that would create substantial R2 read/write amplification; the encrypted original event may remain inside an immutable segment while conforming clients honor the later tombstone.

Forwarding creates a new MLS-encrypted logical message and, for an attachment, a new opaque D1 grant scoped to the destination room. The attachment key and filename remain inside the new MLS ciphertext while the Worker links the grant to the existing encrypted R2 object. No object copy, upload, or extra storage quota is incurred. Multi-select forwarding preserves timeline order, admits at most 100 messages per operation, and queues each encrypted event through the same crash-safe local outbox. If a batch stops partway, the UI reports the completed count and keeps only the unprocessed selection for retry. The server can observe that two opaque attachment references share an object and which rooms are involved. If the source message is retracted, the object remains while a forward grant exists; retracting the last reference schedules the normal durable R2 deletion and returns quota exactly once.

Contact sharing is a distinct `message.contact` event. The namespaced user ID and sender-supplied display-name snapshot are inside the MLS ciphertext; the server sees only the event type, participants, timing, and ciphertext size. The receiver sees the complete account address before opening or starting a direct chat, and room creation still performs the ordinary user lookup, block, invitation-policy, and MLS checks. Forwarding creates a new encrypted logical message and part ID but no dedicated R2 object; like other events, a card can later share a compact historical segment. Contact cards are deliberately excluded from the one-message stranger-request allowance and from local text full-text search because they are structured identity data rather than message prose.

A user can also share a same-origin contact URL or client-rendered QR code from the account panel. The URL carries only the public namespaced user ID as one query parameter; it contains no display-name snapshot, session, device identifier, public/private key, room capability, or message data. Generating, displaying, copying and sharing it are entirely local, deliberately render initials instead of fetching the profile avatar, and perform no Worker, D1, R2 or S3 operation. After authentication, the receiving PWA accepts exactly one canonical same-server ID, removes the parameter from browser history, opens an existing direct room when possible, or performs one D1 profile lookup before entering the ordinary room-creation flow. Manual entry follows the identical exact-ID-only rule; it is not a nickname or prefix search. The new-conversation dialog can also scan the exact same-origin/root-path QR format with the browser camera, stops every camera track after recognition or dismissal, resolves the profile once, and still requires the user to press the final create action. Browsers without `BarcodeDetector` or camera access expose that limitation in context and retain full-user-ID entry. Remote-origin/domain, malformed, duplicate, self and missing-account links fail explicitly. The link grants no authority and cannot bypass blocking, invitation policy, message-request quotas, MLS KeyPackage claims or the one-text/no-attachment stranger boundary. Scanning or resolving an exact manual ID adds one D1 profile read only after strict local validation and never performs an R2/S3 operation.

HTTP(S) URLs in decrypted message text become ordinary keyboard-focusable external links and, when the device-local setting is enabled, the first safe URL also renders as a compact domain/path card. This is intentionally not an Open Graph fetch: the browser derives the ASCII hostname and path from the already-decrypted string without contacting the destination, the Worker never receives a separate plaintext URL, credentials and oversized URLs are not activated, and outbound navigation suppresses the referrer. HTTP cards carry an explicit warning. The preference lives in the account's local PGlite database, is cleared with account data, and is reset for a newly linked device. No thumbnail is downloaded, uploaded, cached in R2, or duplicated during forwarding/history compaction.

A logical message may contain up to ten attachments and at most 100 MiB of plaintext attachment data, with a 25 MiB per-file limit. Image, audio, and generic files share one encrypted attachment part and one `message.file` event type; MIME, size, optional dimensions/duration, and local decoder support determine presentation only after decryption. The file picker, clipboard-image paste, and desktop drag/drop paths all apply the negotiated limits atomically and keep bytes only in page memory until the user sends; staging creates no Worker or object-store request. For ordinary composition and the PWA system-share target, static JPEG/PNG images default to client-side space-saving delivery with an explicit pre-send **original** choice. The optimizer reads at most 256 KiB of framing, refuses animated PNG, unknown framing, edges above 16,384 or more than 40 megapixels, asks the decoder for an at-most 2,048-pixel image, strips source metadata through canvas re-encoding, and selects WebP only when it saves at least 8% and 32 KiB. GIF/WebP and unsafe/unsupported inputs remain byte-exact originals so animation or content is never silently flattened. This transforms the bytes before the existing encryption/upload path: each source still produces exactly one opaque R2/S3 object, never an original-plus-optimized pair or server thumbnail. The client previews supported raster images only up to 12 MiB, 40 megapixels, and a 16,384-pixel edge; larger or invalid images remain ordinary downloadable file cards without entering the image decoder or semantic index. Playable `audio/*` attachments use the audio control, while recorded notes merely add optional duration metadata. The composer encrypts and uploads files sequentially to bound browser memory, then admits one MLS event containing all encrypted attachment metadata. The server sees only a bounded array of opaque object IDs and commits all references to that event in one D1 batch. Previewable image-only messages render as a compact local album; mixed or non-previewable files remain independently downloadable. Forwarding an album creates one D1 grant per part but still copies no R2 objects. If encryption, upload, signing, or local outbox admission fails, the client asks the Worker to bulk-delete every still-uncommitted object from that attempt and return its quota immediately; the seven-day orphan sweep remains the crash fallback.

Every attachment or archive upload now reserves quota and records a D1 `pending_r2_writes` intent containing the exact opaque object key before R2 is touched. The successful metadata commit and intent removal are one D1 batch. If the Worker fails after the R2 write, the scheduled cleanup deletes that known key and atomically returns its reservation; it checks at most 500 queued keys per run and does not list the bucket. Because R2 reads are strongly consistent, an authorized download can identify a genuinely missing object without bucket listing. Repair-capable attachment and archive rows retain their metadata and logical quota while a device is asked for the exact ciphertext; stale legacy intents are still reconciled exactly once. Normal request and maintenance paths therefore use D1 as the object inventory instead of paying for routine bucket-wide listings. An offline operator audit is still recommended for legacy objects created before the intent migration or objects written outside EdgeChat.

### Account data export

`GET /api/v1/account/export` returns the authenticated user's server-held profile, public device identities, personal integrations, blocks, storage accounting, and links to bounded export feeds. Rooms, events, encrypted-object manifests, and encrypted cross-device drafts are independently cursor-paginated with a maximum page size of 500. The account panel writes these pages as NDJSON directly to a user-selected file when the File System Access API is available. Other capable browsers stream into a profile-scoped OPFS file before download; startup, failure, and profile removal clean exact temporary files. Only browsers supporting neither path use a byte-counted whole-Blob fallback, capped at 64 MiB. The staging file contains sensitive account metadata plus ciphertext and should be protected like any downloaded account export, although it cannot decrypt messages by itself. Events are the exact signed ciphertext envelopes available during the user's membership interval. The object feed is built entirely from D1 metadata and provides authorized attachment/segment download paths; listing it never calls R2 `list`, `head`, or `get` and therefore does not create object-read amplification or copy object bodies into the export.

This server export cannot contain plaintext messages, attachment keys, or the OpenMLS provider snapshot because the server never possesses them. It is an administrative data manifest, not a recoverable device backup.

### Encrypted local backup and restore

The account panel can create a version-2 portable `.edgechat-backup` whose sensitive contents are assembled and encrypted entirely in the browser. It contains a gzip-compressed PGlite physical snapshot, the exact device signing/encryption identity, the opaque server-account credential, the OpenMLS provider snapshot, and—by default—every attachment ciphertext and complete archive-segment object already held in this profile's OPFS caches. Users may explicitly choose a smaller database-only backup. The default therefore preserves local plaintext, indexes, attachment keys, durable outboxes, group ratchet state and the exact cached media/history bytes needed after intentional cloud GC or accidental object loss; it cannot include an attachment this device never downloaded or retained. Restore authenticates the outer chunks and bundle framing before switching the local database, refuses to overwrite a different ciphertext under an existing opaque ID, and writes cached objects sequentially to bound memory. Creating a backup writes one small opaque anti-rollback checkpoint to D1, but neither export nor restore reads, uploads, copies, lists or heads any R2/S3 object.

The file begins with a versioned public header and is encrypted in independent 1 MiB AES-256-GCM records. A random 128-bit salt and PBKDF2-SHA-256 with 600,000 iterations derive the wrapping key; each record uses a fresh 96-bit nonce and authenticates the magic, exact header, and chunk index as AAD. Restore verifies every authentication tag, the exact record count and byte length, origin binding, authenticated account metadata, private-key structure, OpenMLS snapshot, and the PGlite `account_state` binding before changing active state. PGlite is restored into a new OPFS/IndexedDB slot first, so a wrong password, corrupt file, invalid database, or account mismatch cannot damage the live slot. Rejected staging databases are closed and deleted by exact name; a slot whose browser handle cannot yet be reclaimed is recorded for retry when the database Worker closes all PGlite connections or at the next Worker start. Activating a valid slot, recording its random restore-commit ID, and putting the replaced slot on that exact-name cleanup ledger happen in one IndexedDB transaction. The restored slot is always excluded from cleanup, so repeated restores do not accumulate complete old message databases or risk deleting the active one. If the database Worker fails after the commit but before its response arrives, the client verifies the ID; if verification is also unavailable it retains the restored identity and interrupted-restore marker and fails closed instead of risking a restored-database/old-MLS split brain.

The backup restores one logical device identity; it is intended to replace that device, not to add another endpoint. Each file carries a one-time D1 checkpoint of how many room events that device had sent. Before touching local storage, restore decrypts the file and asks the server to verify the included account credential, registered public keys, unused checkpoint, and unchanged sent-event count. Login repeats that check and refuses the restore if the source device sent anything afterward, preventing rollback of an old MLS sender state. A successful restore consumes the checkpoint, invalidates the source device's sessions and WebSocket tickets, closes its room sockets, and rotates login to a fresh device credential that is written only to the restored vault. The active source device receives a separate device credential when creating the backup; that credential is deliberately excluded from the file, so a restored copy cannot bypass the checkpoint by using ordinary device-session recovery. The distinct-device link protocol described above is the correct path for adding a second endpoint; it must never import this snapshot. The physical PGlite snapshot is versioned as an EdgeChat format and must be exercised during PGlite upgrade migrations.

### Account deletion

The account panel requires the device-held account credential (or current password for a legacy account) plus an explicit confirmation phrase. Acceptance immediately disables login and all normal authenticated operations. The PWA then removes its push subscription, plaintext PGlite cache, image embeddings, pending ciphertext queues, MLS snapshot, browser identity keys, account credential and access token.

Server cleanup is a resumable D1 job. It repeatedly reconciles its room/object inventory so an upload racing the initial request is not missed, deletes R2 objects by exact key in batches of at most 100 without listing the bucket, and processes at most 20 room Durable Objects per pass. Cron resumes interrupted work. Private rooms lose their attachments, archive segments, D1 rows, sockets, and complete Durable Object storage. Shared rooms and zero-copy forwarded attachments are retained for the remaining members; ownership and quota accounting transfer to the surviving room owner.

Removing a user from a shared room is deliberately not just an ACL change. The account is frozen while the selected surviving owner creates a normal OpenMLS Remove Commit covering every former device. The PWA persists the mutated MLS snapshot and exact signed Commit in PGlite before submission, so reloads retry the same cryptographic operation. Only after every shared room acknowledges its Commit are devices, sessions, push records, and remaining account metadata finalized. The immutable namespaced user ID remains as a non-reusable “Deleted user” tombstone for signed historical events. As with message retraction, deletion cannot erase plaintext or ciphertext already saved by another participant.

### Offline object-store ledger audit

Run the read-only audit occasionally—not in the Worker request path or daily cron—to compare the complete D1 object ledger with current object metadata. For R2:

```bash
export CLOUDFLARE_API_TOKEN='a-scoped-read-only-token'
pnpm run audit:storage -- \
  --account-id "$CLOUDFLARE_ACCOUNT_ID" \
  --database-id "$EDGECHAT_D1_DATABASE_ID" \
  --bucket edgechat-archive \
  --max-list-requests 1000
```

For B2 or another path-style SigV4 provider, keep the Cloudflare token scoped to D1 Read, supply a separate list-only application key, and select `s3`:

```bash
export S3_ENDPOINT='https://s3.<region>.backblazeb2.com'
export S3_REGION='<region>'
export S3_ACCESS_KEY_ID='<list-only-key-id>'
export S3_SECRET_ACCESS_KEY='<list-only-application-key>'
pnpm run audit:storage -- \
  --provider s3 \
  --account-id "$CLOUDFLARE_ACCOUNT_ID" \
  --database-id "$EDGECHAT_D1_DATABASE_ID" \
  --bucket edgechat-archive \
  --max-list-requests 1000
```

Do not reuse deployment credentials. The command paginates D1 in 5,000-row batches and either provider at no more than 1,000 current object names per LIST, then performs a bounded-memory ordered merge. It never fetches object bodies, mutates D1, or deletes objects. `--max-list-requests` defaults to 1,000 and fails the audit before another provider request would exceed that budget; increase it deliberately for buckets above roughly one million current names. The JSON result records the exact LIST request count. Findings distinguish untracked bucket objects, missing objects, size mismatches, and stale write/deletion intents. A 30-minute grace window suppresses normal in-flight differences and can be changed with `--grace-seconds`. Exit code `0` means clean, `2` means integrity findings, and `1` means configuration/API failure. Add `--ndjson` to stream every finding for large audits; the normal JSON report retains at most 100 samples. S3 ListObjectsV2 exposes current names, not every hidden B2 version, so lifecycle/version verification remains a separate provider-console release check.

The segment builder, authenticated decoder, R2 upload/metadata API, HTTP `Range` endpoint, and progressive-indexing primitive are implemented. The PWA now pages older rows from PGlite in 100-message batches and preserves the visible scroll anchor; this path performs no network or object read. The history manifest returns no more than four segment descriptors immediately before its sequence cursor, instead of returning a large room's complete segment catalog. Cloudflare's Worker R2 API receives the HTTP Range header, so the existing decoder reads only framing, encrypted index, and selected chunks. The client requires an exact `206 Content-Range`, enforces a bounded streamed body, and rejects a server or proxy that returns the whole object. After decrypting the index it cross-checks the manifest, header, contiguous chunk extents, sequence mapping, and total object size before any event reaches the MLS processor.

Interactive archive loading for arbitrary old timeline scrolling remains local-first and is not allowed to rewind MLS. Automatic sync recovery is now ordered: every device receives a server-authenticated `joined_seq`, PGlite persists a room-local `processed_through_seq`, and the sync engine refuses to pass a later event into OpenMLS while a sequence is missing. On a real gap it first asks D1 for a bounded archive plan, Range-fetches only the v3 framing/index and required chunks, advances MLS in exact sequence order, and only then consumes the newer durable tail. Normal WebSocket and `/sync` traffic performs no R2 read. OpenMLS still keeps no unlimited past-epoch secrets, so arbitrary historical search indexes only data already decrypted locally instead of rewinding group state.

Automatic compaction is currently an experimental server capability and is disabled by default with `ARCHIVE_COMPACTION_ENABLED=false`. Ordered catch-up is implemented, but the conservative default avoids duplicating durable ciphertext into R2 until an operator intentionally chooses that cost/recovery tradeoff. When enabled, the authenticated session advertises it to the PWA; the Worker rejects new leases and uploads while disabled, so a client cannot bypass the cost guard. After both the encrypted R2 object and D1 segment manifest commit, RoomDO removes the covered duplicate event bodies and keeps only its recent ordering tail; D1 remains the online `/sync` event source until retention GC. Existing non-collected segments remain readable.

Cloud event retention is administrator-configurable per room through `GET|PUT /api/v1/operator/rooms/:roomId/retention`; `retention_days: null` means indefinite retention and remains the default. `minimum_device_copies` selects how many distinct active room devices (1–10, default 1) must report a complete local ciphertext-envelope interval before that interval is eligible for collection. After durable sync, each PWA checks its local ledger in bounded 500-event reads and acknowledges up to 10,000 contiguous sequences through a paginated D1-only endpoint. A gap produces no claim beyond the last locally proven sequence. The daily Cron visits at most 20 least-recently-checked rooms and advances at most 500 events per room, bounded by age, the Nth-highest qualifying device acknowledgement, and complete archive-segment boundaries. Waiting for a whole segment to expire avoids periodic R2 delete-and-rewrite amplification. RoomDO first commits the monotonic floor and increments the lease generation, then D1 deletes matching `room_events` and per-user `room.event` sync rows and carries still-valid coverage into the new generation. A retry reconciles D1 forward from RoomDO if execution stops between those steps. Active repair or compaction leases pause floor advancement. GC is disabled unless acceptance receipts are configured, never deletes device-local PGlite data, and creates no R2 object. Once the floor advances, history and Range endpoints reject logically deleted segments immediately even if physical R2 cleanup is still pending. A lagging device durably stages later ciphertext in a separate PGlite inbox, advances the account-wide sync cursor so unrelated rooms keep working, and leaves only the affected room visibly read-only across reloads. It then requests an exact missing range from another active device of the same user. A source device reads at most 500 contiguous signed ciphertext envelopes from PGlite, zstd-compresses them, and seals the batch to the target's P-256 device key with ECDH/HKDF/AES-GCM. The Worker sees only the room/range/device routing metadata and one opaque temporary object; it never receives local plaintext or MLS private state. The target imports the range in sequence before draining its deferred tail, then acknowledges exact-key deletion. Larger gaps continue as another bounded request. Intentional GC data is restored only to the requesting device and is never inserted back into the authoritative room log.

Peer recovery costs at most one temporary R2 PUT, GET, and DELETE per healthy 500-event batch—not one object per message. Ready objects count against the user's ordinary byte/object quota, expire after 24 hours, and are removed by exact recorded key without bucket listing. If the first authorized GET finds a missing object or invalid provider metadata, the Worker immediately returns the old quota, moves the same recovery back to `pending`, and emits a fresh content-free durable device event. A corrupt object is exact-key deleted; an already missing object incurs no redundant DELETE. Later target polling reads only D1 until a source device claims a new lease and performs one replacement PUT under a new opaque key, so an outage cannot multiply GETs against the bad object. Active clients check work at durable-sync boundaries and every 30 seconds, while requested/ready device events also trigger processing immediately. A recovery request sends an empty, content-free Web Push to the user's other subscribed devices; a completed upload similarly wakes only the target device. The service worker forwards a sync hint to an already open PWA, while an offline endpoint can satisfy the request after its next launch. Push carries no room, sequence, sender, recovery ID, or message content. Transient network failures reuse the same object; only a locally detected authentication/import failure lets the target cancel that object, return its quota by exact-key deletion, and request a replacement beginning after the last durably processed sequence. If no other active device has the complete local range, the room stays read-only and portable backup remains the fallback.

The same Cron stages exact R2 keys for archive segments wholly below the floor and for committed attachments whose source event is below its room floor and whose forwarding grants have all been collected in their own rooms. D1 keeps a compact `(attachment, referencing room, minimum copies)` requirement even after the corresponding event/grant is collected. An attachment object becomes eligible only when the number of distinct active room devices that acknowledged a durable OPFS ciphertext copy satisfies the strongest policy of every source or forwarding room that has referenced it. Raising or lowering a room policy updates its retained requirements; a forwarded attachment therefore cannot fall back to the source room's weaker policy after the grant event disappears. Cron deletes at most 50 known keys per batch, then atomically removes D1 metadata and returns attachment/archive bytes and object counts to the uploader's quota. Failed deletes retain a retry ledger; normal retention performs no bucket `list()` or discovery `head()` request. An attachment still referenced by any surviving forwarded message is retained.

The PWA writes uploaded and downloaded attachment ciphertext to a dedicated OPFS directory before acknowledging retention eligibility. For previewable images, the sending device may also create a maximum 8 KiB thumbnail, with a strict 40 KiB aggregate budget per message, inside the MLS-encrypted payload. This adds no thumbnail object, object write, or object GET; it modestly enlarges the durable event/archive bytes and remains plaintext only on endpoints after MLS decryption. Timeline and media-library views may display that bounded thumbnail immediately, then silently upgrade only when the original ciphertext is already in the profile's OPFS cache. A missing original still renders an explicit size-labelled load control, so scrolling cannot issue speculative R2/S3 GETs. Voice playback and file saving are likewise user initiated. Reads prefer local ciphertext, and concurrent explicit consumers of the same attachment share one cache/object-store task, so a virtual-list remount, image viewer, and save action cannot multiply the same cold GET. If OPFS is unsupported, full, or temporarily unwritable, successfully downloaded ciphertext up to 1 MiB enters an 8 MiB session-only LRU; remounting a group avatar or small attachment then avoids another R2/S3 GET. Each later hit retries only the local persistent write, and retention acknowledgement remains withheld until that write actually succeeds, so volatile memory can never be miscounted as a durable GC copy. Oversized ciphertext bypasses this fallback to cap mobile memory. If local ciphertext fails authenticated decryption, the client removes only that exact cache entry; it does not contact the object store until the user explicitly retries. A successful retention acknowledgement is reused for the rest of the app session; failures remain retryable. Forwarding copies an already cached ciphertext under the destination grant ID locally without downloading or uploading the object, while a cache miss preserves the existing server-side zero-copy reference path. An attachment therefore remains decryptable on the caching device after its cloud object is collected. OPFS contains ciphertext, while the attachment key and optional thumbnail remain inside the E2EE message payload. Linked-device history bundles copy this cache through the same temporary encrypted 16 MiB shards as PGlite rather than creating one R2 object per attachment; after restore, aliases are resolved and canonical IDs are cached and acknowledged too. Local per-room retention still removes decrypted projections and signed repair envelopes, but does not silently erase this independently managed ciphertext cache.

The server policy is administrator-configured rather than demo-specific. An installation may retain cloud ciphertext indefinitely, or run privacy-first GC after a configured age while treating enrolled devices as the long-term archive. A missing sequence **above** the authoritative floor is accidental loss and may be repaired; anything at or below the floor was intentionally collected and must never be resurrected. The repair lease is bound to the current generation so GC invalidates in-flight uploads; an older valid acceptance receipt remains usable for an event still above the floor. R2 cleanup uses the D1 inventory and retry ledger rather than bucket scans. An R2 lifecycle rule remains only a final safety net because lifecycle deletion notifications would still need to reconcile the D1 ledger.

Newly verified events are stored in PGlite as their exact signed ciphertext envelopes, including control events and receipts, in a ledger separate from searchable message projections. Reads for repair are capped and report the first missing room sequence instead of returning a misleading partial range. Finite device-local retention removes matching envelopes. When a valid `EVENT_RECEIPT_KEYRING` is configured, the Room Durable Object also attaches a stable HMAC acceptance receipt after assigning the authoritative sequence. It binds the complete signed client envelope hash, room, sequence, first acceptance time, key ID, and retention generation; a duplicate event returns the original receipt, and tampering invalidates it. Sequence allocation is committed before awaiting WebCrypto so receipt calculation cannot introduce an ordering race.

Client-assisted repair of individual room events is implemented behind the negotiated `history.repair.v1` capability. Daily audit work is capped at 20 least-recently-checked rooms and one 500-sequence range per room; the first pass checks the newest range, then a persisted cursor rotates through older retained history. It compares RoomDO and D1 sequence presence and creates at most one compact D1 repair job per room. Connected room sockets receive a disposable availability hint, while the job remains discoverable after reconnect, so WebSocket is not the durability mechanism. Online PWAs automatically enumerate jobs and compete for a five-minute, device-bound lease. A device requires the complete contiguous local envelope range, selects only server-reported gaps, and uploads at most 20 original events per request. A device without the range releases its lease immediately so another endpoint can try; D1 suppresses that same device for 24 hours while leaving the task immediately visible to other devices. The Worker verifies the original device signature and HMAC acceptance receipt, while RoomDO atomically enforces the lease, authoritative floor, and current generation. Repair inserts missing ciphertext into RoomDO/D1 only: it does not emit a new room event, replay an MLS control event, or create an R2 object. Conflicting history and stale leases are rejected, completed jobs and attempt markers are removed together, and intentional GC below the floor cannot be undone.

Attachment relationship metadata follows the same accidental-loss boundary without duplicating object data. Restoring an original file event rebinds its existing attachment row from the signed envelope's opaque attachment ID; the ciphertext object is neither read nor rewritten. Forward grants no longer cascade away when a `room_events` row is accidentally deleted, so the destination remains authorized and zero-copy sharing remains intact. Intentional retention still deletes those grants explicitly by authoritative room sequence before collecting the event, and can reclaim the underlying R2 object only after every surviving source/forwarding policy is satisfied.

New attachment and archive-segment uploads pin a SHA-256 digest of the already encrypted bytes in D1 and ask R2 to verify the same checksum during `put()`. Before an archive upload, the compactor first writes the exact encrypted segment to a dedicated OPFS cache; a successful upload is not considered device-held until its acknowledgement succeeds, and an interrupted acknowledgement is retried after later sync. A missing object discovered by an authorized read no longer destroys metadata or decrements logical quota: the Worker returns a temporary-unavailable response, creates one idempotent D1 repair job, and emits a content-free hint. That D1 job is also a download circuit breaker: later attachment or Range requests return the same retryable response without another R2 GET until repair completes, preventing refreshes and multiple devices from multiplying Class B operations during an outage. Devices only see jobs for ciphertext they previously acknowledged caching in OPFS. One device acquires a five-minute D1 lease, verifies its local byte length and digest before upload, and restores the same opaque R2 key with a conditional write. The Worker streams the request body directly into that PUT and gives R2 the D1-pinned digest for independent verification, avoiding a 25 MiB attachment or 12 MiB segment buffer in Worker memory. A normal repair is one PUT; only a race in which another request already restored the key performs one HEAD to verify that exact object. A stale or corrupt local cache loses its possession acknowledgement so another device can try. Repair performs no bucket listing, creates no duplicate object, and does not alter quota. A retention/account-deletion race removes a newly written orphan before returning an error. Legacy objects uploaded before digest pinning remain deliberately non-repairable rather than accepting unverifiable bytes.

Deployments without a valid `EVENT_RECEIPT_KEYRING` continue messaging but do not advertise, audit, or accept room-event repair. The active receipt key signs new events while historical keyring entries keep old repair receipts verifiable, so planned rotation does not retroactively destroy repairability. Attachment and archive-object repair are independently negotiated as `attachments.repair.v1` and `archive.repair.v1` and do not depend on receipt secrets. Linked-device bundle v3 copies exact archive ciphertext too; if the administrator intentionally collected the server segment, the receiving device keeps that local archive but a 404 is never treated as permission to resurrect it. Re-encrypting plaintext is never a valid repair.

For device enrollment, Cloudflare remains the dependable bootstrap and rendezvous path. The existing ECDH-encrypted, temporary R2 handoff can copy the approving device's local history to the new device and deletes each shard after staging; normal `/sync` supplies current room state and recent events. A future peer transport can replace the bulk-history data path without changing the snapshot/event formats. Native iroh endpoints can use direct QUIC and LAN discovery, but current browser/PWA iroh endpoints cannot open raw UDP sockets or use mDNS and therefore use a relay. Browser-local direct transfer should be treated as a separate, opportunistic WebRTC DataChannel transport with Cloudflare signaling and a relay/cloud fallback, not as a prerequisite for correct enrollment.

When enabled, compaction runs opportunistically while an owner PWA is active: a dedicated browser Worker performs zrip and AES-GCM work off the UI thread, while the room Durable Object serializes five-minute compaction leases so only one device can build a range. D1 chooses a contiguous range by event count and encoded size, leaving a recent realtime tail. Jobs and keys are checkpointed in PGlite; failed jobs release their lease and never block messaging.

Before upload, the owner generates a random segment key, fetches one bounded list of active room-device public keys from D1, and embeds independently authenticated device wraps in the same segment object. This removes one durable MLS control event per segment and creates no extra R2 object. Header and key-envelope/index bytes are coalesced into two metadata Range reads before chunk reads, so wrapping does not add an object request. The browser supplies the complete segment SHA-256; the Worker buffers only the bounded framing/key-envelope prefix needed to validate recipients and range metadata, then replays that prefix and streams the remaining ciphertext through one fixed-length, checksum-verified conditional R2 PUT. Uploads remain bound to the lease token, preallocated segment ID, device, exact sequence range, size and digest, and reject overlaps or conflicting ID reuse. After a timeout or transport failure the client retries once with the identical ID, bytes and digest; if D1 already committed, the Worker answers from that row without another R2/S3 call. If both responses fail, an exact resolution request either proves that commit and continues the OPFS retention acknowledgement, or marks the pending D1 claim cancelled before one exact-key DELETE. A concurrently finishing PUT rechecks both the claim and its lease at the commit boundary, then deletes itself when either is no longer valid. A page crash during `uploading`, an unknown server result, and an interrupted `uploaded` retention acknowledgement are durable PGlite recovery states; startup/reconnect resolves them before admitting another compaction for the same room, so its OPFS repair reference cannot be overwritten. Committed/absent resolution is D1-only, pending cancellation uses one exact DELETE, and the path never uses LIST or deletes a committed segment. A newly linked device receives the approving endpoint's locally held archive keys through the encrypted PGlite history handoff; a newly invited user still does not receive pre-join archive keys. Each accepted event is charged once to its sender's independent encrypted-event byte/count quota; per-member sync rows contain only compact event-ID pointers, and `/sync` hydrates them from the canonical D1 row. Failed reservations are released and Cron reconciles ambiguous stale claims.

Every HTTP API request now carries the client's current and minimum-server protocol versions. Worker responses carry the corresponding server range, while authenticated session payloads advertise bounded feature and attachment limits. A pre-negotiation v1 server is treated conservatively as single-attachment and receives the legacy scalar metadata fields; incompatible ranges fail before storage work. This supports stale installed-PWA assets during controlled rollouts without creating a second API or speculative protocol abstraction.

## Native share target

The installable PWA declares a `POST multipart/form-data` Web Share Target for text, links, and files. Its service worker consumes the navigation request locally, validates the same 16,000-character, ten-file, 25 MiB-per-file and 100 MiB-total limits as the composer, and stages the complete selection in a dedicated browser IndexedDB under an opaque one-time ID. Nothing is sent to the Worker, D1, or R2 at this stage. After login, a focused dialog lists every staged file and total size, requires an explicit destination-room choice, allows the accompanying text to be edited, and uploads/encrypts only after the user presses the final send button. Cancel and successful send delete the staged record; send failure keeps it for retry. Inaccessible records expire logically after 24 hours and are reclaimed on the next share-target use. Version-one single-file staged records remain readable after an application update.

The account panel reflects the real browser installation state instead of showing a fake universal install button. Chromium's deferred installation prompt is available only after the browser declares the app eligible; iPhone and iPad users instead see the native Share → Add to Home Screen path, while other browsers receive a concise browser-menu fallback. Standalone display mode and the `appinstalled` event suppress further prompts.

Before login or registration is enabled, the application proves that the profile-scoped PGlite database can complete a read-only open. A 0.5 KiB loader starts before the much larger PGlite Wasm/data runtime and reports that its import is still pending while those immutable assets arrive: 60 seconds without a loader/runtime signal terminates the database Worker, while a separate 180-second absolute deadline prevents a stalled download from waiting forever. Either failure enters the non-destructive recovery screen; retry is a full document restart, so an abandoned initializer cannot race a replacement Worker. Encrypted-backup recovery remains available after a watchdog failure by creating a fresh Worker that validates a separate staging database without opening the current slot, then closes immediately; interrupted recovery uses the same isolation rule. This watchdog is entirely local and performs no Worker, D1, R2 or S3 request.

An incoming Web Push sets only an anonymous application badge and uses the generic notification “有新的加密活动” because its empty payload deliberately cannot distinguish a message from device-recovery work or carry an exact room count. It also sends an in-origin sync hint to an already open PWA. Once the PWA completes local sync, it replaces the marker with the exact sum of PGlite unread projections, or clears it when nothing remains unread. Browsers without the Badging API silently keep working. A newly downloaded service worker no longer takes over an active chat: the UI waits for the current PGlite/OPFS startup to settle before offering **更新并重启**, persists the current text/reply/quote/edit draft first, and refuses to reload while an unpersisted attachment or voice recording is present. Startup-recovery and signed-out states still receive the prompt once local initialization has completed. If that local draft write fails, activation fails closed before `SKIP_WAITING` and the current version remains active. Each production build injects its complete hashed application-asset list—including PGlite and OpenMLS Wasm/data—into a build-versioned shell cache. Installation succeeds atomically or leaves the previous worker active; immutable assets are cache-first, navigation remains network-first, and a missing script/Wasm/data file is never replaced with the HTML shell. Byte-range asset requests deliberately bypass that full-response cache, so an offline range read fails instead of silently receiving an invalid complete `200` object. The optional external semantic-search model stays lazy and is not required to open messages offline. These installation and lifecycle operations are entirely device-local and add no D1 or R2 traffic beyond normal sync.

Text/link shares create no R2 object. A confirmed file selection follows the ordinary client-side attachment encryption and quota-reservation path and creates exactly one opaque attachment object per original file. Multi-file shares become one logical MLS message, use the album layout only when every attachment passes the local bounded image-preview policy, and inherit immediate failed-upload reclamation. The share target never silently drops extra files and does not create thumbnails, previews, or duplicate R2 objects.

## Installed-PWA file handling

On platforms implementing the File Handling API, the installed PWA registers only common image, audio, video, PDF and text extensions. An operating-system “open with EdgeChat” launch reads at most eleven file handles—one beyond the ten-file product limit—and writes either the bounded files or a content-free limit error into the same device-local staging database used by the Web Share Target. The app then navigates to the existing confirmation flow. It never registers itself as a catch-all handler, does not associate encrypted backup files with the send flow, and does not call the Worker or create R2 objects before the user chooses a conversation and presses send. Unsupported browsers ignore the manifest member and retain the normal picker/share-target paths.

## Web Push privacy

Pushes use VAPID and deliberately carry an empty payload. The service worker shows a generic “new encrypted activity” notification and the application retrieves ciphertext through `/sync`. No sender name or message preview is sent to the push provider. Whether decrypted previews should ever be shown is a separate, explicit user privacy choice.

After a user explicitly enables notifications, the PWA reconciles the browser endpoint with the current device's D1 subscription on later authenticated starts and when the account panel opens. It never prompts automatically. VAPID-key changes replace the browser subscription, expired server rows are recreated, and logout/device cleanup removes local renewal state. `pushsubscriptionchange` can run while no authenticated window is open: it uses a random device-scoped renewal capability stored locally, while D1 stores only its SHA-256 hash. That capability can replace only the same device's validated public-HTTPS endpoint and keys; it cannot read ciphertext, send messages, or call other account APIs. Renewal is anonymously rate-limited, revoked devices and deleting/deleted accounts are rejected, and notification delivery remains an optimization over durable `/sync`. These operations use D1 and browser IndexedDB only and never read or write R2.

## Future federation boundary

Federation is not implemented. `FederationTransport` is isolated in `packages/protocol`; `LocalFederationTransport` is the only implementation. Client APIs, crypto state, room persistence, and the Room Durable Object do not depend on a server-to-server protocol.

A later transport can route a remote participant's event to the room home server, where the existing Room Durable Object validates membership and assigns the authoritative sequence before replication. This preserves the single-writer model and avoids Matrix state resolution. MIMI-inspired provider-to-provider transport can be evaluated without rewriting local rooms or clients.

## Local development

Requirements: Node.js 22+, pnpm 11, Rust with the `wasm32-unknown-unknown` target, and a Cloudflare account for deployed resources.

```bash
rustup target add wasm32-unknown-unknown
pnpm install
pnpm run dev
```

The Vite client and Worker dev server run together. Worker startup first applies every pending migration to the local Wrangler D1 store non-interactively, so a newly pulled schema cannot leave authentication behind the hot-reloaded code. `pnpm run db:migrate:local` remains available as an explicit repair/inspection command. `SERVER_NAME` defaults to `localhost`, so local IDs look like `@alice:localhost`.

Useful checks:

```bash
pnpm run typecheck
pnpm test
pnpm run build
```

`pnpm run db:types` rebuilds `apps/worker/src/database.generated.ts` from all D1 migrations through `kysely-codegen`; the full check verifies that the committed type file is current. It also verifies the immutable D1 migration SHA-256 manifest, contiguous numbering, and explicit rollout policy for newly recorded expand/data/contract migrations. Local PGlite databases have their own contiguous, SHA-256-pinned migration history: each pending migration runs in one transaction, a client refuses a database written by a newer schema version, and restored databases pass through the same migration gate before their staging slot becomes active. Published local migration SQL is immutable; add a new entry in `packages/db/src/migrations.ts` instead of editing `LOCAL_SCHEMA` or an earlier entry. These local checks use OPFS/IndexedDB only and create no D1 or R2/S3 traffic. `pnpm run build` compiles the Rust crate for `wasm32`, builds the PWA, and performs a Wrangler deployment dry run.

Production migrations remain an explicit operator step before deployment. If application code reaches a D1 database that is structurally behind, the Worker returns a sanitized `503 server_upgrade_required` response instead of a generic authentication failure or raw SQL detail. This diagnosis uses the failing request itself and performs no extra D1 or R2/S3 operation.

## Cloudflare deployment

Create resources and replace the placeholder IDs/names in `apps/worker/wrangler.jsonc`:

```bash
pnpm exec wrangler d1 create edgechat-db
pnpm exec wrangler r2 bucket create edgechat-archive
pnpm exec wrangler d1 migrations apply edgechat-db --remote --config apps/worker/wrangler.jsonc
pnpm exec wrangler secret put EVENT_RECEIPT_KEYRING --config apps/worker/wrangler.jsonc
```

`EVENT_RECEIPT_KEYRING` is a JSON object mapping 1–16 public key IDs to independent 32–4096-byte secrets; `EVENT_RECEIPT_KEY_ID` selects the active signer. Start with one key. To rotate, upload a keyring containing the old and new keys, change `EVENT_RECEIPT_KEY_ID` to the new ID, then verify `GET /api/v1/operator/event-receipt-keys`. Keep an old verification key until every receipt it signed is intentionally below its room's authoritative retention floor; with indefinite server retention, retain it indefinitely. Malformed, oversized, weak, or active-key-missing keyrings fail closed and remove `history.repair.v1` from advertised capabilities without interrupting normal messaging. The operator endpoint exposes IDs and validation state only, never secret material.

Set `SERVER_NAME` to the public host before accepting registrations. Configure VAPID values (`VAPID_SUBJECT`, `VAPID_PUBLIC_KEY`) in non-secret config and add the private JWK as a secret:

```bash
cd apps/worker
pnpm exec wrangler secret put VAPID_PRIVATE_JWK
pnpm exec wrangler secret put OPERATOR_TOKEN
cd ../..
pnpm run deploy
```

Scheduled maintenance lives in the reusable `runScheduledTasks()` function.
The Worker's own `scheduled()` handler and the private named
`ScheduledTasksService` RPC entrypoint both call that function, so an
account-level Cron Worker can consolidate triggers through a Service Binding
without exposing an HTTP maintenance endpoint. Scheduled work is idempotent;
remove the standalone trigger only after the central dispatcher has been
observed invoking the RPC successfully.

Use at least 32 random bytes for `OPERATOR_TOKEN`; it protects the storage-operations API and is intentionally separate from user sessions. Do not reuse the checked-in all-zero D1 placeholder. Keep the VAPID private JWK, Operator token, and any future recovery secrets out of source control.

## Implemented API surface

Accounts/devices, current-password-verified password changes, the D1/DO side of capability-protected device linking, scoped personal bots, idempotent MLS KeyPackage claiming/replenishment, Welcome-based room creation, MLS Commit-based group member add/remove and resumable per-device removal, signed ciphertext events and sender tombstones, durable cursor sync, recent history, encrypted attachment upload/download/deletion, client-compaction leases, segment upload/range download, push subscribe/unsubscribe, one-time WebSocket tickets, and room WebSockets are implemented below `/api/v1`.

Storage accounting has separate object and encrypted-event budgets. Operator storage responses expose event bytes/counts, and per-user overrides accept `event_quota_bytes` and `event_limit` alongside the object limits.

The separately authenticated Operator API exposes `GET /api/v1/operator/readiness` for a one-statement D1 inventory and durable-queue age SLO snapshot, `GET /api/v1/operator/storage` for paginated D1-ledger totals including pending writes/deletions, `GET /api/v1/operator/rooms` for retention policy, active-device coverage, and archive-ledger use, and `PUT`/`DELETE /api/v1/operator/users/:userId/storage-limit` for setting or resetting a user's byte/object limits. `GET /api/v1/operator/reports` pages metadata-only abuse reports by status; `PUT /api/v1/operator/reports/:reportId` records a confirmed or dismissed resolution plus an append-only operator action. `GET /api/v1/operator/appeals` pages credential-verified, metadata-only account appeals; `PUT /api/v1/operator/appeals/:appealId` records an approved/denied action and can optionally clear a matching login lock. `GET /api/v1/operator/login-locks` lists active or historical failure state without credentials, and `POST /api/v1/operator/users/:userId/login-unlock` idempotently clears it while preserving an append-only audit snapshot. The server cannot supply message plaintext to reviewers. These routine operations query D1 and never list or read the R2 bucket. Lowering a limit below current usage is non-destructive: existing ciphertext remains, while subsequent object reservations are rejected until usage falls below the limit.

The HTTPS-only CLI exposes the same bounded operations:

```bash
EDGECHAT_URL=https://chat.example.com EDGECHAT_OPERATOR_TOKEN="$OPERATOR_TOKEN" \
  pnpm run operator -- reports --status open --all

EDGECHAT_URL=https://chat.example.com EDGECHAT_OPERATOR_TOKEN="$OPERATOR_TOKEN" \
  pnpm run operator -- report REPORT_ID --resolution confirmed --note "repeat unsolicited requests"

EDGECHAT_URL=https://chat.example.com EDGECHAT_OPERATOR_TOKEN="$OPERATOR_TOKEN" \
  pnpm run operator -- appeals --status pending --all

EDGECHAT_URL=https://chat.example.com EDGECHAT_OPERATOR_TOKEN="$OPERATOR_TOKEN" \
  pnpm run operator -- appeal APPEAL_ID --resolution approved --unlock-login --note "verified login-lock appeal"

EDGECHAT_URL=https://chat.example.com EDGECHAT_OPERATOR_TOKEN="$OPERATOR_TOKEN" \
  pnpm run operator -- login-locks --status active --all

EDGECHAT_URL=https://chat.example.com EDGECHAT_OPERATOR_TOKEN="$OPERATOR_TOKEN" \
  pnpm run operator -- login-unlock '@alice:example.com' --note "verified owner"
```

The small operator CLI calls only those authenticated Worker endpoints. Keep its token in the environment rather than command history:

```bash
export EDGECHAT_URL=https://chat.example.com
export EDGECHAT_OPERATOR_TOKEN='a-long-random-operator-token'
pnpm run operator -- readiness
pnpm run operator -- rooms --policy finite --all
pnpm run operator -- retention '!opaque-room-id-1234:example.com'
pnpm run operator -- retention '!opaque-room-id-1234:example.com' --days 30 --minimum-device-copies 2
pnpm run operator -- retention '!opaque-room-id-1234:example.com' --days indefinite
```

Remote URLs must use HTTPS; plain HTTP is accepted only for localhost development. `rooms --all` follows bounded cursor pagination. The separate `pnpm run audit:storage` command is the exceptional, request-budgeted offline integrity audit that deliberately lists the selected object provider and should not be part of routine retention administration.

Operational SLOs, structured security-event privacy rules, D1 Time Travel rollout preflight, and the staging disaster-recovery exercise are documented in [docs/OPERATIONS.md](docs/OPERATIONS.md). The readiness snapshot is one D1 statement and never inspects R2; this keeps routine monitoring predictable even for long-lived personal archives.

Protocol/control events remain in the encrypted event stream but are filtered from the visible chat timeline. Encrypted delivery/read receipts, local unread state, and ephemeral WebSocket typing presence are implemented.
