# Security policy

EdgeChat is currently a preview. It has not received an independent cryptographic or application-security audit and must not yet be represented as a finished Delta Chat replacement.

## Reporting

Do not disclose a suspected vulnerability in a public issue before the operator has had a reasonable opportunity to investigate it. A production deployment should publish a monitored private security contact in this section before accepting external users.

Reports should include the affected version, reproduction steps, expected impact, and whether the issue could expose message plaintext, device identity material, attachment keys, or membership state. Never include another user's real message data or credentials in a report.

## Dependency policy

- Commit `pnpm-lock.yaml` and install in CI with `pnpm install --frozen-lockfile`; production deployments must not resolve unreviewed versions during deployment.
- Run `pnpm run security:audit` on every dependency update and on a recurring schedule. High or critical production findings block release unless a written, narrowly scoped exception explains reachability and compensating controls.
- Review major dependency upgrades separately, especially OpenMLS, PGlite, Transformers.js, zstd/Wasm, Wrangler, and service-worker tooling.
- Verify the Rust dependency graph with `cargo audit` in release CI once that tool is installed; do not silently skip the job.
- Keep generated Wasm reproducible from checked-in Rust sources and verify the OpenMLS transcript/smoke tests after toolchain changes.

## Browser policy

The deployed PWA sends a restrictive Content Security Policy and hardened API response headers. PGlite currently loads PostgreSQL Wasm extensions that compile generated JavaScript with `eval`, so the CSP contains a documented `script-src 'unsafe-eval'` exception. This is a tracked dependency constraint, not permission for application code to use dynamic evaluation. Remove it after PGlite provides a compatible CSP-safe build.

Remote connections are restricted to the same origin, Hugging Face model-download hosts, and a version-pinned jsDelivr URL for the Transformers.js ONNX runtime used by local image semantic search. The ONNX Wasm file is loaded only on first semantic-search/index use and is cached by Transformers.js; keeping it external avoids Cloudflare's 25 MiB per-static-asset limit and does not consume R2. Message text, images, embeddings, MLS state, and search queries remain client-side; only public model/runtime files are fetched from those hosts. Deployments requiring fully self-hosted first-run semantic search must mirror and pin those public files on a separate static origin before removing the corresponding CSP hosts.

## Cryptographic boundary

The server authenticates devices, authorizes ciphertext envelopes, orders room events, and stores encrypted objects. It must never receive room keys, attachment keys, decrypted message bodies, local search indexes, or semantic embeddings. New protocol changes require tamper, replay, stale-epoch, and cross-room authorization tests. Release tests execute the generated OpenMLS Wasm—not only the native Rust success path—and cover application replay, wrong-group delivery, ciphertext and membership-Commit tampering, stale Commits, out-of-order message generations, strict TLS framing, and the inability of a removed member to send or decrypt the next epoch. These tests reduce regression risk but are not an independent protocol audit.

Local profiles are an application-data isolation boundary inside one browser origin, not an OS security boundary. Every profile uses a distinct UUID namespace for tokens, private device keys, PGlite storage, OPFS ciphertext caches, link staging and Push state. Only one profile is active, because the exclusive Web Lock and browser Push subscription are origin-wide. Switching profiles detaches the old Push subscription before selecting the new namespace; inactive profiles do not background-sync. Removing a local profile clears its plaintext message/search database, keys and caches, but a compromised browser origin, extension, OS account or storage implementation can still cross these logical namespaces.

Archive metadata and complete encrypted segment objects are untrusted local cache input. Cached framing and encrypted index bytes are accepted only when their room, sequence range and object size match the authenticated server descriptor and the index AEAD plus structural checks pass. Complete OPFS segments additionally authenticate every selected chunk before decompression. A corrupt cache entry is removed and retried through the same bounded exact-`206` network path; no cached offset or length may cause an unbounded allocation or whole-object fallback.

OpenMLS device snapshots are secret, untrusted local input at restore time. Import rejects oversized or structurally invalid snapshots, unknown fields/versions, duplicate or unbacked group identifiers, duplicate provider-storage keys, and identities outside the supported bound before exposing a client. The authenticated portable-backup envelope remains responsible for origin/account binding and rollback prevention; snapshot validation does not make an unauthenticated state file safe.

Decrypting an incoming MLS event and projecting it into PGlite spans the MLS vault and local SQL storage, which cannot share one browser transaction. A transient PGlite staging row therefore binds the exact signed envelope and plaintext to both the pre- and post-transition MLS snapshots. Recovery accepts only a vault matching one of those snapshots, restores the post-state before replaying the idempotent projection, and fails closed on any other combination. The row has the same endpoint-compromise exposure as the normal local plaintext cache and is removed after projection or profile cleanup; it is never uploaded.

Cross-device drafts are not MLS room messages because that would reveal unfinished text to every room member. A source device instead seals the current draft or deletion tombstone independently to each active device of the same account with ephemeral P-256 ECDH, HKDF-SHA-256 and AES-256-GCM, and signs the complete envelope. The Worker verifies membership, the exact active human-device set, envelope bounds, and the registered source signature before replacing the target's current D1 ciphertext. It sees room/source/target IDs, timing and ciphertext length but not draft text, reply/quote targets, or whether the envelope means deletion. Draft outbox coalescing is local and no draft path uses R2/S3. This does not provide endpoint compromise protection or cryptographic deniability, and independent review is still required.

Voice capture exists only in the active browser session. Microphone tracks are stopped on send, cancel, navigation to another room, recorder error, and component disposal. Encoded audio is then handled as a client-encrypted attachment; the server can observe its ciphertext size, upload/download timing and room-scoped object authorization, but not the audio, filename, duration, MIME type or attachment key. Playback is user-initiated so merely rendering or scrolling history does not fetch voice objects from R2.

Device-local retention is a local exposure limit, not remote deletion. Its transaction removes expired decrypted message projections, full-text terms, attachment metadata, and semantic vectors while retaining the sync cursor, processed-event IDs, and content-free sender-retraction tombstones needed to prevent historical resurrection. It does not remove ciphertext or attachments from the server, other members, exports, backups created before cleanup, or already saved files. The UI must keep that distinction visible and must not describe local cleanup as disappearing messages.

## Authorization boundary

Ordinary room-event submission cannot publish MLS membership control events; device add/revoke and group membership Commits are accepted only by their dedicated state-machine endpoints. This prevents an otherwise valid member signature from advancing a Room Durable Object's MLS epoch outside the matching D1 membership operation. Group membership changes require the current owner in both D1 and the Room Durable Object.

Invitation preferences are server-visible account metadata because the Worker must reject unwanted KeyPackage claims before cryptographic material is reserved. They control future invitations only and cannot revoke a room or plaintext already delivered. Blocks remain symmetric for interaction authorization but the API only exposes `blocked_by_me` to avoid confirming another person's block decision.

## Portable backup boundary

Portable backups are opt-in endpoint exports and never transit the EdgeChat server or R2. New device keys are WebCrypto-extractable solely so the client can place their private JWK material inside an AES-256-GCM backup together with the OpenMLS and PGlite snapshots. This weakens protection against script execution in the application origin compared with non-extractable keys; CSP, dependency review, and XSS prevention are therefore part of the key boundary. Older non-extractable identities fail closed instead of producing a misleading partial backup.

Backup confidentiality is only as strong as its user-chosen password. The format uses a fresh salt, PBKDF2-SHA-256 with 600,000 iterations, fresh nonces, chunk-index-bound AAD, and authenticated length/framing checks, but it cannot prevent offline guessing of a weak password. The UI requires at least 12 characters and warns users to separate the password from the file. Restore is restricted to the same application origin and authenticated account binding, validates the OpenMLS snapshot, and stages PGlite in a new storage slot before activation.

Restoring stale MLS sender state is unsafe. Backup creation therefore records a bounded, opaque D1 checkpoint containing the device's sent-event count. A password-authenticated preflight rejects an invalid, consumed, revoked, wrong-key, or stale backup before local storage activation; login repeats the authoritative check in case state changed between preflight and activation. The first restored login succeeds only if that count is unchanged and the checkpoint has not been consumed; it then invalidates existing sessions/tickets, closes room sockets, and issues a fresh live-device credential. Backup creation also rotates the source's live credential, but does not place it in the backup. Consequently, a restored file cannot omit its checkpoint and masquerade as the still-current device. The file is a replacement-device recovery mechanism, not a device-cloning mechanism. This control consumes a few D1 rows but never stores backup bytes or creates R2/S3 objects.

Device linking is a separate capability flow. Possession of the link secret permits polling and uploading additional one-time MLS KeyPackages, but cannot approve the device, read rooms, or mint a session. Approval requires an existing user session; room access then requires one ordered MLS Add Commit per room. Final session claim additionally requires a signature from the proposed device key over the exact link, device ID, and access-token hash. Link secrets belong in a request header rather than a URL so normal access logs and referrers do not capture them. The UI must compare the canonical public-key fingerprint and require an explicit confirmation; scanning a QR code is not approval. Approved partial links cannot be silently discarded because completed MLS additions require a corresponding removal operation.

The QR URL keeps its secret after `#`, and the approving client discards that secret after extracting the public link ID. Camera access is allowed only for the same-origin PWA through `Permissions-Policy`; browsers without `BarcodeDetector` use the paste fallback. The new endpoint persists its claim token before submission, and the approving endpoint persists the exact MLS Commit and pre/post snapshots before publication. Unapproved/KeyPackage-waiting links expire; approved partial links remain resumable by another authenticated device of the same account after another fingerprint check.

Linked-device history does not export the approving endpoint's OpenMLS state or private device keys. Its fixed gzip PGlite snapshot is split into 16 MiB plaintext shards; each shard is encrypted in authenticated 1 MiB records with a key derived from the approving device's private P-256 ECDH key and the new device's public ECDH key. Link, transfer, shard, source, and target IDs are bound through HKDF and AEAD associated data. The server can observe timing, shard count, and compressed byte counts, but not plaintext history, search indexes, attachment/archive keys, or either ECDH private key.

Temporary shard objects are quota-accounted and streamed through the Worker. The target authenticates and decrypts a shard before durably staging its plaintext in device-local IndexedDB and acknowledging exact-key R2 deletion; interrupted transfers resume from D1 plus local staging. This staging has the same local-device exposure as the plaintext PGlite database and is cleared after atomic import. Abandoned remote shards are deleted by exact key during link cleanup. The imported physical database is sanitized before activation so source-device MLS state, sending/removal/link outboxes, compaction jobs, push state, and device-local room preferences are never cloned.

In-place peer recovery after administrator retention is narrower than device linking. It transfers only an exact contiguous range of already signed ciphertext envelopes, never decrypted projections, search indexes, attachment keys, or a device's OpenMLS state. Batches are capped at 500 events and 32 MiB before compression, zstd-compressed, then authenticated to the requesting device with P-256 ECDH, HKDF-SHA-256, and AES-256-GCM bound to the recovery, room, device, and sequence identifiers. The server necessarily observes those identifiers, the requested sequence range, timing, compressed ciphertext size, and which same-account device supplied it. An active device of the same account is therefore inside this recovery trust boundary. The target still processes the recovered envelopes through normal ordered MLS handling; failed authentication or invalid ordering leaves the room blocked. Temporary R2 objects expire after 24 hours and are deleted by exact key after successful import. A target may cancel an unusable object; cancellation deletes the recorded key and returns quota before a replacement can be requested, while an upload racing cancellation fails its lease commit and removes its own orphan. Recovery below the server retention floor is device-local and must never repopulate the authoritative cloud room log.

Peer-recovery wake-ups reuse empty Web Push requests. No payload, room ID, sequence range, recovery ID, sender, or message text is sent to the push service. The provider still observes that a subscribed endpoint received a wake-up and its timing. Because an empty push cannot safely distinguish message delivery from recovery work, the service worker displays generic encrypted-activity copy and asks an open client to run ordinary authenticated sync. Expired push endpoints returning `404` or `410` are removed from D1.

Unknown-user direct conversations are quarantined as message requests. Before acceptance the requester may persist one signed MLS-encrypted text event, but no attachment, archive segment, typing signal, reply, reaction, receipt, or other message event. The server enforces hourly and outstanding-request limits. A claim-context reservation is inserted and charged before the target's one-time MLS KeyPackage is claimed; retrying the same room ID is idempotent, while abandoned reservations expire with abandoned KeyPackage claims. Groups may contain only users with an already established accepted/shared relationship. This keeps pending abuse in D1 and the Room Durable Object and prevents it from allocating R2 objects. Rejecting stops future events; reporting also creates a user block. D1 necessarily reveals requester/recipient IDs, request status and timing, report category, an optional reported event ID, and the operator's resolution/note. It never receives the report's message plaintext because the server cannot decrypt the event. Operator listing and resolution are token-isolated, paginated, D1-only, and each resolution appends an audit action.
